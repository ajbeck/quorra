[SignIn]

End-to-end OAuth 2.0 device-authorization sign-in for AWS IAM Identity Center, executed as five Sonnet-sized scopes-of-work that ship as one PR. Every secret in the macOS Keychain; every doc citation grounded in the official Apple HIG, SwiftUI reference, and AWS API docs.

01Overview

Phase 1 replaces the "Sign-in not yet implemented in this build" stub in SessionDetailView with a real device-authorization flow. The user clicks Sign in with IAM Identity Center on a session, Safari opens to the verification URL, Quorra polls AWS until the user completes the browser step, then the access token (and refresh token, if issued) lands in the macOS Keychain.

The work is split into five scopes — A through E — small enough that a Sonnet subagent can execute each one cleanly with the plan + project context attached. After each phase the senior reviewer (the main agent) runs /simplify on the diff, applies fixes, and folds the lessons into the next phase's prompt so the same mistakes don't repeat.

research basisThis plan is grounded in the research report at docs/IAMIdentityCenterDeviceAuth.html. That doc is the authoritative reference for the OIDC protocol mechanics, AWS API field names, and Keychain layout choices. Read it once before kickoff.

02Scope & non-goals

In scope

  • New IAMIdentityCenter library product in the existing QuorraCore SwiftPM package.
  • An actor Keychain wrapper for the shared access group $(AppIdentifierPrefix)dev.ajbeck.quorra.shared.
  • A hand-rolled OIDCClient built on URLSession covering RegisterClient, StartDeviceAuthorization, and CreateToken (initial grant only).
  • An actor IdentityCenterService with one public verb: signIn(sessionName:startUrl:region:scopes:clientName:verificationHandler:).
  • App-side @Observable @MainActor CredentialsModel exposing signIn(session:) and an inFlight dictionary.
  • SessionDetailView changes: replace the status-section stub with the inline sign-in panel.
  • Tests at every layer.

Out of scope (deferred to later PRs)

  • Refresh. No refresh_token grant in CreateToken; no liveToken on the actor; no proactive refresh task. Phase 3.
  • Sign-out. Phase 2 — trivial once UI exists.
  • Sidebar status dot. Phase 2 — needs SessionAuthStatus + status(forSession:).
  • SSO Portal calls + role credentials. No ListAccounts / GetRoleCredentials; no RoleCredentials type. Phase 4.
  • Profile-detail credential reveal. Phase 4 — needs role credentials.
  • IMDS endpoint subsystem. Phase 5.
  • CLI sign-in. Same module, but quorra-cli doesn't depend on IAMIdentityCenter until the CLI work begins.
do notPhase 1 must not introduce SessionAuthStatus, status(forSession:), sidebar dots, or role credentials. Each is a real piece of work that gets its own scope; smuggling them into Phase 1 makes review harder and the diff fatter.

04Architecture: layers

Two layers, mirroring the existing AWSConfigINI + ProfilesModel split:

LayerLives inOwns
IAMIdentityCenter (low-level)Packages/QuorraCore/Sources/IAMIdentityCenter/URLSession-backed OIDC client, Keychain wrapper, actor IdentityCenterService, error type, data shapes. Pure logic + I/O. No SwiftUI. Sendable throughout.
CredentialsModel (app-side)quorra/App/Credentials/@Observable @MainActor presenter. Owns inFlight dictionary, calls into the actor, publishes UI-friendly state.

Module dependency direction

Strict one-way: quorra (app) → CredentialsModel → IAMIdentityCenter (library) → URLSession + Security.framework. No cycles. IAMIdentityCenter imports nothing from the app — not SwiftUI, not Observation, not AppKit.

Sendable boundaries

  • Actor. IdentityCenterService is an actor — all calls cross an isolation boundary; everything it returns is Sendable.
  • Keychain. actor Keychain — same property.
  • Data shapes. Every public struct in IAMIdentityCenter is Sendable, Hashable, Codable with all-value-typed stored properties.
  • App side. CredentialsModel is @Observable @MainActor. Inputs/outputs to/from the actor are Sendable; the model itself is main-actor-isolated so SwiftUI consumes it directly.

Codable strategy

  • JSONEncoder.dateEncodingStrategy = .secondsSince1970 on encode/decode of stored types.
  • AWS wire types (response envelopes, error bodies) live as internal struct Wire.RegisterClientResponse, Wire.CreateTokenResponse, Wire.OAuthErrorResponse in a Wire.swift file.
  • Public surface stays clean: callers never see wire types.

Redaction in CustomStringConvertible

Every secret-bearing public struct (StoredOIDCClient, StoredSSOToken) implements CustomStringConvertible with the secret fields elided:

Redaction.swift swift 
extension StoredSSOToken: CustomStringConvertible {
    public var description: String {
        "StoredSSOToken(session: \(sessionName), expiresAt: \(expiresAt), hasRefresh: \(refreshToken != nil))"
    }
}

Pure ergonomics — kills a class of print(token) footguns and os.Logger default-redaction inversions.

06Errors

Single enum, untyped throws in public API per TSPL guidance, conforms to Error + Sendable + LocalizedError.

  • .network(URLError)Wraps URLSession-level transport errors.
  • .malformedResponse(String)JSON decode failed or missing required fields.
  • .httpStatus(Int, body: String?)Unexpected HTTP status with no parseable AWS error envelope.
  • .authorizationPendingRFC 8628 — internal; absorbed by the polling loop.
  • .slowDownRFC 8628 — internal; loop adds 5s to the interval.
  • .accessDeniedUser refused at the IdP. Surface as cancellation, not error.
  • .expiredDeviceCodeUser did not complete the flow before expiresIn.
  • .invalidGrantProgrammer / state error.
  • .invalidClientOIDC client registration is gone or expired. (Phase 3 will retry; Phase 1 surfaces.)
  • .userCancelledUser pressed Cancel in the inline sign-in panel.
  • .deviceFlowTimedOutWall clock since StartDeviceAuthorization exceeded expiresIn.
  • .awsError(code: String, description: String?)Forward-compat fallback for AWS error codes we don't have a typed case for.
  • .keychainItemMissing(service: String, account: String)Expected row not present.
  • .keychainStatus(OSStatus)Keychain operation failed at the OS level.
  • .keychainMalformed(reason: String)Stored payload didn't decode (e.g. partial-write recovery).

LocalizedError

Every case provides an errorDescription and, where applicable, a recoverySuggestion. The descriptions are user-facing, not developer-facing; the alert rendered by SessionDetailView reads from these.

polling internals.authorizationPending and .slowDown are part of the public enum but should never escape the actor — they're thrown by the wire decoder in OIDCClient.createToken and caught by the polling loop in IdentityCenterService.signIn. Consumer-facing: a successful signIn or one of the terminal errors.

07Actor API (Phase 1 surface)

actorIdentityCenterService

public actor IdentityCenterService { public init(keychain: Keychain, urlSession: URLSession = .shared, clock: any Clock<Duration> = ContinuousClock()) }

funcsignIn(...)

public func signIn( sessionName: String, startUrl: URL, region: String, scopes: [String], clientName: String = "Quorra", verificationHandler: @Sendable (DeviceVerification) async -> Void ) async throws -> StoredSSOToken

Drive the full device-grant flow. Reuses cached StoredOIDCClient from Keychain when present and not near-expiry; otherwise calls RegisterClient. Calls StartDeviceAuthorization, invokes verificationHandler exactly once with the resulting DeviceVerification, then polls CreateToken every interval seconds until the user completes the browser step or the device code expires. Persists token to Keychain, returns it.

funccancelSignIn(sessionName:)

public func cancelSignIn(sessionName: String) async

Cancels an in-flight signIn for the given session. The signIn call throws .userCancelled.

Keychain layout (Phase 1 subset)

Itemserviceaccount
OIDC client (per region)dev.ajbeck.quorra.oidc-client<region>
SSO token (per session)dev.ajbeck.quorra.sso-token<sessionName>

Each record is stored as a single JSON-encoded Keychain row. Atomic per record by construction — there's no intermediate state where some fields are persisted and others aren't, so partial-write recovery is automatic: a missing row throws .keychainItemMissing; a corrupt row throws .keychainMalformed. Both cases force a fresh registration or sign-in.

design noteAn earlier draft of this plan called for field-per-row records to stay under Keychain's per-item size limits. In practice our payloads are well under those limits (a typical SSO bearer JWT plus refresh token is < 4 KB; Keychain's kSecValueData tolerates much more). Atomicity-per-record removes a class of partial-write bugs and is preferred.
access groupEvery SecItem* call must include kSecAttrAccessGroup = "$(AppIdentifierPrefix)dev.ajbeck.quorra.shared", evaluated at sign time. The app and CLI both read from this group; missing the attribute makes items invisible to the other binary.

CPhase C — IdentityCenterService.signIn

Subagent · Sonnet

~200 LOC source · ~280 LOC tests

What gets built

  • actor IdentityCenterService with init, signIn, cancelSignIn.
  • Polling state machine inside signIn: per RFC 8628 §3.5, sleep interval first, increment by 5s on .slowDown, terminate on .expiredDeviceCode / .accessDenied, throw .deviceFlowTimedOut when wall clock since StartDeviceAuthorization exceeds expiresIn.
  • OIDC client cache: read StoredOIDCClient for region from Keychain; if missing or secretExpiresAt - now < 7 days, call RegisterClient and persist.
  • Cancellation: [String: Task<StoredSSOToken, Error>] map keyed by sessionName; cancelSignIn finds the task and cancels it. The polling loop honors Task.checkCancellation() and re-throws CancellationError as .userCancelled.
  • Persists the StoredSSOToken on success, returns it.

Acceptance criteria

  • Happy path: stub responses for RegisterClient → StartDeviceAuthorization → 2× authorization_pending → CreateToken success. signIn returns the token; verificationHandler was invoked exactly once with valid DeviceVerification; token landed in Keychain.
  • slow_down: stub returns slow_down on first poll, success on second. The actor's interval increased by 5s after the first slow_down.
  • Timeout: stub returns authorization_pending indefinitely; service throws .deviceFlowTimedOut after wall clock exceeds expiresIn. Use the injected Clock to fast-forward.
  • Cancellation: parent Task calls cancelSignIn mid-poll; the polling loop exits and signIn throws .userCancelled.
  • Cached client reuse: write a StoredOIDCClient to Keychain manually; signIn does not call RegisterClient.
  • Expired client refresh: write a StoredOIDCClient with secretExpiresAt < now + 7 days; signIn does call RegisterClient.
  • Sendable conformance: passing the verificationHandler closure across actor isolation compiles cleanly under strict concurrency.

08Subagent execution loop

  1. Main agent writes the prompt

    For phase N, the main agent assembles a self-contained prompt: project rules preamble + this plan as context + the phase's specific scope/files/acceptance criteria + cumulative review findings from phases 1..N-1.

  2. Sonnet subagent executes

    Spawned via the Agent tool with model: "sonnet". It reads the plan, reads referenced project files, writes code, writes tests, runs swift build + swift test, returns a summary of what it changed.

  3. Senior review with /simplify

    Main agent invokes /simplify on the diff. Looks for: dead code, premature abstraction, missing tests, copy drift from the HIG citations, Sendable / actor-isolation mistakes, secrets in error messages or log output, partial-write recovery missed, redaction missed in description.

  4. Apply fixes inline

    Main agent fixes anything actionable directly. Anything ambiguous gets escalated to the user via AskUserQuestion.

  5. Xcode UI step (if any)

    Walk the user through any required pbxproj-side changes (e.g. adding a target dependency through the Project Editor). Subagent never touches pbxproj or workspace files.

  6. Capture lessons → next prompt

    Anything the reviewer fixed becomes a "do not" line in phase N+1's prompt. The cumulative findings list grows monotonically; phase E sees the union of all prior lessons.

  • Phase 3 is lazy on read only. Proactive refresh waits for Phase 5.

Phase 4 — SSO Portal + role credentials + reveal UI

  • Add PortalClient with listAccounts, listAccountRoles, getRoleCredentials. RoleCredentials public type with Wire-namespaced ms-vs-s adapter for the expiration field.
  • Add actor.roleCredentials(forSession:accountId:roleName:region:) async throws -> RoleCredentials — reads role-creds cache, mints fresh via GetRoleCredentials if near-expiry (liveToken first if SSO token also stale).
  • Add a "Credentials" Section to ProfileDetailView for SSO-derived profiles. DisclosureGroup with privacySensitive() on each secret Text; redaction toggled via .environment(\.redactionReasons, isRevealed ? [] : .privacy). Per-row copy buttons + a "Copy as environment variables" action.
  • No auto-hide; no clipboard self-clear (Apple Passwords precedent — neither is HIG-mandated).
  • Long-term-keys profiles get no credentials section (separate concern — secrets live in the file in v1).

Phase 5 — IMDS endpoint subsystem

This is the biggest deferred chunk and the one that anchors the actor's design. Worth capturing the contract carefully so Phase 1's actor doesn't accidentally pre-empt it.

  • One endpoint per profile. Each profile that the user enables IMDS-for gets its own IMDSEndpoint instance bound to a unique 127.0.0.1:<port>.
  • The endpoint owns its own refresh loop. Not the credentials actor. No activate/deactivate handshake. IMDSEndpoint.start() mints the initial creds and schedules Task.sleep until expiration - 7.5 min; on wake, re-mint via service.roleCredentials(...); loop until stop().
  • 7.5-minute pre-rotation budget. AWS IMDS guarantees ≥5min; we go a little wider to give ourselves margin against round-trip variance on flaky networks. Source: AWSEC2/UserGuide/instance-metadata-security-credentials.html ("We make new credentials available at least five minutes before the expiration of the old credentials.").
  • Failure response. When refresh fails, the endpoint serves HTTP 200 OK with body {"Code": "AssumeRoleUnauthorizedAccess", "LastUpdated": "...", "Type": "AWS-HMAC", "Message": "<truthful reason>"} — never 4xx for credential-content failures, and never secret material on a failure response. Source: IAM/UserGuide/troubleshoot_iam-ec2.html.
  • HTTP 4xx / 5xx reserved for IMDS-protocol-level failures (missing IMDSv2 token, version-pinned paths, unknown metadata paths, server bugs).
  • IMDSv2 by default. PUT /latest/api/token with X-aws-ec2-metadata-token-ttl-seconds; subsequent GETs require the bearer token. IMDSv1 supported as fallback per project CLAUDE.md.
why this matters for Phase 1The credentials actor's API in Phase 1 must be complete enough for Phase 5 to plug into without surgery. Specifically: roleCredentials(...) is the verb the IMDS endpoint will call on its refresh loop. We don't implement it in Phase 1, but the Phase 1 design must not introduce anything that would block adding it later (no global mutable state, no hidden refresh tasks, no implicit caching the IMDS endpoint can't see through).
