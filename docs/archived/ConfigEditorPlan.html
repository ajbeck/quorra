01Overview

Quorra today launches into SetupView, lets the user pick ~/.aws, persists a security-scoped bookmark, and lands on a placeholder MainView that lists folder contents. This iteration replaces the placeholder with a real working surface: a sidebar of SSO-session-grouped profiles, a profile/session detail pane backed by the typed Profile / SSOSession models from AWSConfigINI, and a save round-trip that exercises the full fcntl-locked atomic write path.

The defining design choice is the mode contract: every user starts in Edit & Manage mode (the default), but they may pick Read Only during setup or in Settings at any time. Read Only renders the same forms as labels — the app reads, browses, and (eventually) serves credentials, but never writes the AWS files. Edit & Manage prepends # Managed by Quorra on first save and may canonicalize formatting.

The plan is broken into ten phases ordered by dependency. Each phase is small enough to land in a single session, and most close with a short acceptance check the implementer can run before moving on.

02Scope & non-goals

In scope

  • Mode preference (Edit & Manage / Read Only) persisted to UserDefaults.standard.
  • Mode card on SetupView + radio-group toggle in Settings scene.
  • Standard macOS Settings { ... } scene reachable via ⌘, and the App-menu Settings… item.
  • End the existing setup flow on the new MainView (no placeholder).
  • NavigationSplitView with a sidebar and a single detail pane.
  • Sidebar: List(selection:) with one Section { OutlineGroup } for SSO Sessions, plus flat Sections for Long-term keys / Other.
  • Profile detail pane: single Configuration tab with a typed Form.
  • SSO session detail pane: same Form shape, against SSOSession.
  • Save round-trip via AWSConfigINIDocument.update(at:flavor:_:) with re-parse on success.
  • Toolbar refresh button (⌘R) preserving selection.
  • Read Only mode renders forms as LabeledContent + a top notice Section with an Open Settings… button.
  • Three additive changes inside the AWSConfigINI package, tested in-package before app work begins.

Out of scope (deferred)

  • Add Profile / Delete Profile / search — the iteration is read+edit only.
  • Credentials tab — depends on Keychain wiring not built yet.
  • Activity tab — no event stream yet.
  • IMDS Server view & runtime — separate iteration.
  • SSO OIDC device-code flow — Renew / Sign out buttons are deferred.
  • FSEvents file watching — refresh button + after-save re-parse only.
  • App↔CLI bookmark sharing via App Group — bookmark stays in app-only UserDefaults.
  • Raw INI editor — power-user feature, additive later.
  • Profile rename — section-header editing is out.
  • Region / source-profile / session autocomplete — free-text fields.
scope guardIf the implementer feels the urge to add an "Add Profile" button or a search field "since we're already here" — don't. Each deferred item has a real reason; relitigating during implementation invalidates the plan.

P1.2 — AWSConfigINIError: LocalizedError

SwiftUI's data-driven alert overload takes E? where E: LocalizedError. Conforming the typed error makes the alert API "just work" without a wrapper. The error is already an enum with associated URL / String values; this conformance is purely additive.

AWSConfigINIError+LocalizedError.swift swift 
extension AWSConfigINIError: LocalizedError {
    public var errorDescription: String? {
        switch self {
        case .fileNotFound(let url):
            return "Couldn't find the file at \(url.path(percentEncoded: false))."
        case .ioError(let url, _):
            return "Couldn't read or write \(url.lastPathComponent)."
        case .lockTimeout(let url):
            return "Couldn't get exclusive access to \(url.lastPathComponent). Another process may be holding the lock."
        case .readOnly(let url):
            return "\(url.lastPathComponent) is open in Read Only mode and can't be written."
        case .decodeError(let message):
            return "Couldn't read this profile: \(message)"
        case .encodeError(let message):
            return "This value can't be saved: \(message)"
        case .malformedInput(let message):
            return "Couldn't parse the file: \(message)"
        }
    }

    public var recoverySuggestion: String? {
        switch self {
        case .lockTimeout: return "Try again in a moment."
        case .readOnly:    return "Switch to Edit & Manage in Settings to make changes."
        case .ioError(_, let underlying): return underlying.localizedDescription
        default: return nil
        }
    }
}

Tests to add in AWSConfigINIErrorTests.swift:

  • For each AWSConfigINIError case: assert errorDescription is non-nil and contains identifying substring (URL last component, message text).
  • Assert recoverySuggestion is set for .lockTimeout, .readOnly, .ioError and absent for the rest.
  • Cast through error as LocalizedError to confirm the conformance is reachable via the protocol.

06Phase 2 — Mode preference

P2

ModePreferenceStorage value type + tests

depends on: P1

The user's mode (Edit & Manage / Read Only) is non-secret app config. Apple's UserDefaults docs say: "You use this system to store nonsensitive information, such as app-specific configuration details." That's exactly the right home. Mirror the existing BookmarkStorage pattern so the code reads as a family.

why not @AppStorageThe view-level wrapper is fine for views, but AppModel needs to read the persisted value at init time before any view body runs. A small storage struct accessed from AppModel mirrors the existing BookmarkStorage shape and is the right place to put the persistence logic.

New file: App/Preferences/ModePreferenceStorage.swift

ModePreferenceStorage.swift swift 
import Foundation
import AWSConfigINI

struct ModePreferenceStorage {
    static let key = "dev.ajbeck.quorra.managedMode"

    static let `default` = ModePreferenceStorage(defaults: .standard)

    let defaults: UserDefaults

    init(defaults: UserDefaults) { self.defaults = defaults }

    /// Returns the persisted mode, or `.managed` (the documented default) when absent or unparseable.
    func load() -> ManagedMode {
        guard let raw = defaults.string(forKey: Self.key) else { return .managed }
        switch raw {
        case "managed":  return .managed
        case "readOnly": return .readOnly
        default:           return .managed
        }
    }

    func save(_ mode: ManagedMode) {
        switch mode {
        case .managed:  defaults.set("managed",  forKey: Self.key)
        case .readOnly: defaults.set("readOnly", forKey: Self.key)
        }
    }

    func clear() { defaults.removeObject(forKey: Self.key) }
}

New tests: Tests/QuorraAppTests/ModePreferenceStorageTests.swift

Use Swift Testing (@Test), inject UserDefaults(suiteName:) per BookmarkStorageTests:

  • load_returns_managed_when_no_value_present — fresh suite returns .managed.
  • save_then_load_round_trips_managed and ...readOnly.
  • clear_removes_value — after clear, load() returns .managed.
  • load_returns_managed_for_unrecognized_string — write a junk string directly via the same key, assert .managed.
  • One round-trip test that reads both BookmarkStorage and ModePreferenceStorage from the same suite to confirm key namespacing doesn't collide.

  2. Storage struct is Sendable-compatible (struct of UserDefaults + String key) and compiles in Swift 6 strict-concurrency mode.

07Phase 3 — AppModel + setup card

P3

Mode lives on AppModel; SetupView grows a mode card

depends on: P1, P2

Mode is parallel to phase on AppModel — they have orthogonal lifecycles. A user in .error still has a mode preference; toggling mode never changes phase. Apple's per-property tracking on @Observable means views observing only mode won't redraw when phase changes (per the migration doc).

P3.1 — Extend AppModel

AppModel.swift swift 
import Foundation
import Observation
import AWSConfigINI

@Observable
final class AppModel {
    private(set) var phase: AppPhase
    private(set) var mode:  ManagedMode

    @ObservationIgnored private let bookmarkStorage: BookmarkStorage
    @ObservationIgnored private let modeStorage:     ModePreferenceStorage
    @ObservationIgnored private var currentAccessURL: URL?

    init(
        bookmarkStorage: BookmarkStorage      = .default,
        modeStorage:     ModePreferenceStorage = .default
    ) {
        self.bookmarkStorage = bookmarkStorage
        self.modeStorage = modeStorage
        self.phase = .setup
        self.mode  = modeStorage.load()
    }

    init(
        bookmarkStorage: BookmarkStorage      = .default,
        modeStorage:     ModePreferenceStorage = .default,
        initialPhase:    AppPhase,
        initialMode:     ManagedMode?         = nil
    ) {
        self.bookmarkStorage = bookmarkStorage
        self.modeStorage = modeStorage
        self.phase = initialPhase
        self.mode  = initialMode ?? modeStorage.load()
    }

    // Existing API — unchanged behavior, but completeSetup grows a mode parameter.
    func resolveStoredBookmark() async { /* unchanged */ }

    func completeSetup(selectedFolder url: URL, mode newMode: ManagedMode) async {
        modeStorage.save(newMode)
        self.mode = newMode
        do {
            let data = try bookmarkStorage.makeBookmark(for: url)
            bookmarkStorage.save(data)
            currentAccessURL = url
            phase = .ready(url)
        } catch {
            phase = .error(.bookmarkResolutionFailed(underlying: error))
        }
    }

    func setMode(_ newMode: ManagedMode) async {
        modeStorage.save(newMode)
        self.mode = newMode
    }

    func resetToSetup() async { /* unchanged */ }
    func retryResolution() async { /* unchanged */ }
}

Mode-flip ordering invariant: persistence first, then state. If save succeeded but the published value wasn't updated, an observer reading both would briefly see disagreement. Persisting first means the worst case is "old observer state, correct disk state" — recoverable on next read.

09Phase 5 — ProfilesModel

P5

@Observable ProfilesModel + derived sidebar groups

depends on: P1, P3

This phase introduces a second observable root next to AppModel. ProfilesModel owns the parsed AWS files and the derived view-models the sidebar consumes. Apple's environment slot is per-type (per View/environment), so two distinct types coexist trivially. The motivation is granular tracking — views observing only profilesModel.groups won't redraw when appModel.mode changes.

P5.1 — Type definitions

Three small Identifiable / Hashable view-model types and the ProfilesModel itself. Live under App/Profiles/.

SidebarSelection.swift swift 
enum SidebarSelection: Hashable {
    case session(name: String)   // SSO session selected

ProfileNode.swift swift 
struct ProfileNode: Identifiable, Hashable {
    let id: String            // profile name (e.g. "dev", "default")
    let profile: Profile     // decoded; merged across files if applicable
    let origin: Origin

    enum Origin: Hashable {
        case configOnly         // section in ~/.aws/config only
        case credentialsOnly    // section in ~/.aws/credentials only
        case both                // in both files; credentials wins per-key
    }

    /// The flavor that should receive a write for this profile.
    /// In v1: always .config when both, since we don't edit credentials-file fields.
    var writeFlavor: FileFlavor {
        switch origin {
        case .configOnly, .both:  return .config
        case .credentialsOnly:    return .credentials
        }
    }
}

P5.2 — ProfilesModel

ProfilesModel.swift swift 
@Observable
final class ProfilesModel {
    private(set) var configDocument:      AWSConfigINIDocument?
    private(set) var credentialsDocument: AWSConfigINIDocument?
    private(set) var groups:              SidebarGroups = .empty
    private(set) var loadState:           LoadState = .idle

    enum LoadState: Equatable {
        case idle
        case loading
        case loaded
        case failed(AWSConfigINIError)
    }

    @ObservationIgnored private var currentFolder: URL?

    func load(folder: URL) async {
        currentFolder = folder
        loadState = .loading
        do {
            let configURL      = folder.appending(path: "config")
            let credentialsURL = folder.appending(path: "credentials")

            configDocument      = try readOrEmpty(configURL,      flavor: .config)
            credentialsDocument = try readOrEmpty(credentialsURL, flavor: .credentials)

            groups = derive(config: configDocument!, credentials: credentialsDocument!)
            loadState = .loaded
        } catch let error as AWSConfigINIError {
            loadState = .failed(error)
        } catch {
            // shouldn't happen — readOrEmpty narrows to AWSConfigINIError
            loadState = .failed(.malformedInput(error.localizedDescription))
        }
    }

    func reload() async {
        guard let folder = currentFolder else { return }
        await load(folder: folder)
    }

    private func readOrEmpty(_ url: URL, flavor: FileFlavor) throws -> AWSConfigINIDocument {
        if FileManager.default.fileExists(atPath: url.path(percentEncoded: false)) {
            return try AWSConfigINIDocument(contentsOf: url, flavor: flavor)
        } else {
            return AWSConfigINIDocument(empty: flavor)
        }
    }

    // derive(...) — the classification ladder; spec'd in P5.3
}

P5.3 — Classification ladder (the derive function)

The ladder is in Section 16 of this plan. Restated for the implementer:

  1. For each section S in config + credentials whose name names a profile (after stripping the profile  prefix in the config flavor, or always-as-given in credentials):
    1. Build a merged Profile: decode the config-side section first, then overlay credentials-side values for any keys present in both. Use the existing AWSConfigINIDecoder; for the merge, decode each side, then write a small key-by-key picker that prefers credentials.
    2. Tag the resulting ProfileNode.origin based on which file(s) the section appeared in.
  2. SSO-rooted: profile.ssoSession != nil && !profile.ssoSession!.isEmpty → bucket under that session name.
  3. Long-term keys: origin == .credentialsOnly OR the section in config has aws_access_key_id. (The latter is rare in ~/.aws/config but legal.)
  4. Other: everything else.

For SSO sessions themselves: enumerate all [sso-session NAME] sections in the config document; create one SSOSessionNode per session, even if no profiles reference it (a session with zero profiles still appears, just without a chevron). Decoding may fail if a session is malformed; in that case set session: nil and still surface the row.

Sort order: SSO sessions in the order their [sso-session NAME] sections appear in the config file. Profiles within an SSO session: alphabetical, with default first if present. Long-term keys / Other: alphabetical, default first.

11Phase 7 — Sidebar grammar

P7

Sections + OutlineGroup with unified selection

depends on: P5, P6

The sidebar combines a hierarchical OutlineGroup for the SSO Sessions section with flat ForEach rows for Long-term keys / Other. Per the documentation, OutlineGroup participates in the enclosing List's selection. The hierarchical List(_:children:selection:) initializer cannot be combined with sibling Sections — it owns the entire list. We use List(selection:content:) instead.

composition trapThe shape List(sessions, children: \.profiles, selection: $sel) { ... }; Section { ... } does not compile. The hierarchical initializer's Content is fixed to a single OutlineGroup. The correct shape is List(selection: $sel) { Section { OutlineGroup(...) }; Section { ForEach(...) } }.

P7.1 — SidebarView body

SidebarView.swift swift 
struct SidebarView: View {
    @Binding var selection: SidebarSelection?
    @Environment(ProfilesModel.self) private var profilesModel

    var body: some View {
        List(selection: $selection) {
            ssoSessionsSection
            longTermKeysSection
            otherSection
        }
        .listStyle(.sidebar)
    }

    @ViewBuilder private var ssoSessionsSection: some View {
        if !profilesModel.groups.ssoSessions.isEmpty {
            Section("SSO Sessions") {
                ForEach(profilesModel.groups.ssoSessions) { session in
                    if session.profiles.isEmpty {
                        // no chevron — flat row, still selectable as a session
                        SessionRow(session: session)
                            .tag(SidebarSelection.session(name: session.id))
                    } else {
                        DisclosureGroup {
                            ForEach(session.profiles) { profile in
                                ProfileRow(profile: profile)
                                    .tag(SidebarSelection.profile(name: profile.id))
                            }
                        } label: {
                            SessionRow(session: session)
                        }
                        .tag(SidebarSelection.session(name: session.id))
                    }
                }
            }
        }
    }

    @ViewBuilder private var longTermKeysSection: some View {
        if !profilesModel.groups.longTermKeys.isEmpty {
            Section("Long-term keys") {
                ForEach(profilesModel.groups.longTermKeys) { profile in
                    ProfileRow(profile: profile)
                        .tag(SidebarSelection.profile(name: profile.id))
                }
            }
        }
    }

    @ViewBuilder private var otherSection: some View {
        if !profilesModel.groups.other.isEmpty {
            Section("Other") {
                ForEach(profilesModel.groups.other) { profile in
                    ProfileRow(profile: profile)
                        .tag(SidebarSelection.profile(name: profile.id))
                }
            }
        }
    }
}
DisclosureGroup vs OutlineGroupThe Apple-research agent flagged "don't hand-roll DisclosureGroup inside List(selection:)." But that warning is about flat uses where the label doesn't get a .tag(...). Here we explicitly tag both the label (the session row) and the children (profile rows), so selection works for both. OutlineGroup with the children keypath is also acceptable but ties data shape to the keypath — using DisclosureGroup + ForEach with explicit .tags gives us flexibility to render different row types per level (which we want — a session row carries different metadata than a profile row).

P9.2 — Save implementation

Per-section save. Wraps the call in AWSConfigINIDocument.update(at:flavor:.managed). The function lives on ProfilesModel so it can re-derive groups after the write.

ProfilesModel+Save.swift swift 
extension ProfilesModel {
    /// Persist a Profile change for the given node. Re-reads + re-derives on success.
    func save(_ updated: Profile, for node: ProfileNode) async throws(AWSConfigINIError) {
        guard let folder = currentFolder else {
            throw .ioError(URL(filePath: "/dev/null"),
                          underlying: NSError(domain: "Quorra", code: -1))
        }
        let flavor = node.writeFlavor
        let url = folder.appending(path: flavor == .config ? "config" : "credentials")
        let sectionName = flavor.profileSectionName(for: node.id)

        try AWSConfigINIDocument.update(at: url, flavor: flavor, mode: .managed) { doc in
            try AWSConfigINIEncoder().encodeProfile(updated, named: node.id, into: &doc)
        }

        await reload()
    }

    func save(_ updated: SSOSession, for node: SSOSessionNode) async throws(AWSConfigINIError) {
        guard let folder = currentFolder else {
            throw .ioError(URL(filePath: "/dev/null"),
                          underlying: NSError(domain: "Quorra", code: -1))
        }
        let url = folder.appending(path: "config")
        try AWSConfigINIDocument.update(at: url, flavor: .config, mode: .managed) { doc in
            try AWSConfigINIEncoder().encode(updated, into: &doc, section: "sso-session \(node.id)")
        }
        await reload()
    }
}

Calling site in the view:

ProfileDetailView+Save.swift swift 
private func save() async {
    do {
        try await profilesModel.save(draft, for: node)
        // reload() will re-derive groups and `node` will be replaced — onChange re-seeds draft
    } catch let err as AWSConfigINIError {
        saveError = err
        isPresentingSaveError = true
    } catch {
        saveError = .malformedInput(error.localizedDescription)
        isPresentingSaveError = true
    }
}
typed-throws noteAWSConfigINIDocument.update(at:flavor:_:) uses Swift 6.2 typed throws — throws(AWSConfigINIError). The view's do/catch must catch the typed error, not Error. The let err as AWSConfigINIError form works for the typed-throw bridge, but the second catch for error is unreachable in practice — keep it for compiler exhaustiveness if needed.

16Design notes

Load-bearing decisions, with the rationale that justifies them. Cite when discussing during review.

●UserDefaults for non-secret config ●Settings { } scene for ⌘, ●Two @Observable models ●List(selection:) + OutlineGroup ●Form + LabeledContent ●Confirmation/Cancellation toolbar ●navigationSubtitle("Edited") ●Typed-error LocalizedError alert ●Per-section save ●Credentials wins on merge

Why UserDefaults, not Keychain, for mode

The mode is non-secret app configuration. Apple's UserDefaults doc says: "Don't store personal or sensitive information as settings… Store personal or sensitive information in the person's Keychain instead." Mode is the inverse — it's exactly what UserDefaults is for. Putting it in Keychain would conflate two storage tiers and confuse the codebase.

Why Settings { } instead of an in-window destination

The mockup showed Settings as a sidebar item; we deliberately diverged. Apple's Settings scene auto-wires ⌘, and the App-menu Settings… item — both user expectations on macOS. The mockup is design-direction, not behavior spec; the HIG approach takes priority.

Why two @Observable models

Per the Observation migration doc, SwiftUI tracks reads per-property. Splitting AppModel (phase / mode / bookmark) from ProfilesModel (parsed documents / sidebar groups) means views observing only the sidebar groups don't redraw when the mode flips. Granular tracking + separation of concerns are the same gain in this case.

Why List(selection:) + OutlineGroup instead of List(_:children:selection:)

The hierarchical List(_:children:selection:) initializer's Content is fixed to a single OutlineGroup; it cannot accept sibling Sections. Our sidebar mixes a hierarchical SSO Sessions section with flat Long-term keys / Other sections. The correct shape is List(selection: $sel) { Section { ... }; Section { ... } } with DisclosureGroup or OutlineGroup inside the section that needs hierarchy.

Why Form + LabeledContent

Form is documented as "a container for grouping controls used for data entry, such as in settings or inspectors." LabeledContent is documented for "a read-only or read-write value, and its label identifies or describes the purpose of that value." They are exactly the structured-edit + read-only-display primitives our editor needs. No custom layout required.

Why navigationSubtitle("Edited") not "•"

AppKit's NSWindow.isDocumentEdited renders the dot inside the close button — there is no documented "•" suffix in the title string. SwiftUI's navigationSubtitle is the macOS-shaped place to surface the dirty cue inline. Cleaner, no AppKit bridge.

Why scenePhase is not in the reload triggers

On macOS, scenePhase.background means the scene is being terminated, not "the user switched windows." Wiring reload-on-background-to-active would only fire on app termination — useless for our intent. The macOS-correct primitive when we eventually want this is EnvironmentValues.appearsActive. v1 ships without it.

Why credentials-file values override config values on merge

This is AWS's documented precedence — see Configuration setting precedence. The merge happens in our view-model layer (ProfilesModel.derive), not in AWSConfigINI. The package's job is faithful per-file representation; AWS's domain-specific precedence is consumer logic. Keeping the package single-purpose preserves write-safety: writes target the originating file, the merge is read-only.

Why the writer isn't byte-exact

Inherited from AWSConfigINI's deliberate trade-off: canonical writes preserve comments and order but normalize alignment, separator spacing, and quoting. The managed/read-only mode pair gives the user explicit control over whether Quorra reformats their file. This iteration ships Edit & Manage as the default, so first-time users will see canonicalization on first save — the # Managed by Quorra header makes this expectation visible.

Why per-section save instead of autosave

NSDocument autosaves in place; Quorra is not a document app. Per-section save matches the user's mental model of "I edited this profile, I clicked Save, the change is on disk" and minimizes lock-acquire churn. Autosave on every keystroke would re-acquire the fcntl lock and re-prepend the managed header repeatedly — wasteful and surprising.

What was deliberately not built

Add Profile, Delete Profile, Search, Credentials tab, Activity tab, IMDS Server view, SSO OIDC flow, FSEvents file watching, App↔CLI bookmark sharing, raw INI editor, profile rename, autocomplete. Each has a real reason it's deferred (listed in §02). The implementer should not relitigate during implementation; if a deferred item starts to feel necessary, raise it in the review pass — the senior reviewer with /simplify can decide whether to absorb it into v1 or push to v2.
