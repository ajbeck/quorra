02Decisions log

Settled during the planning interview. Each is grounded in either Apple/Swift documentation, AWS API documentation, or the research docs (IAMIdentityCenterDeviceAuth.html, SSODeviceAuth.html).

D1 — SessionAuthStatus shape

Five-case enum with a canRefresh boolean carried by both signedIn and expired. The boolean is what lets the UI disambiguate "expired, will fix itself" from "expired, please sign in." Fewer cases than carving them as separate variants, and the boolean is the axis that matters for UI decisions.

SessionAuthStatus.swift swift 
public enum SessionAuthStatus: Sendable, Hashable {
    case signedOut
    case signedIn(expiresAt: Date, canRefresh: Bool)
    case expired(expiredAt: Date, canRefresh: Bool)
    case signingIn      // user-initiated device flow
    case refreshing     // background silent refresh in flight
}

Rejected alternatives:

  • Separate expiredRefreshable / expiredNeedsSignIn cases. Six cases instead of five and the boolean is more pattern-match friendly in views.
  • Drop signingIn, let CredentialsModel.inFlight stay the source. SessionRow would have to read two sources; centralizing in the actor keeps the icon's logic in one place.
  • Add expiringSoon. The detail-view countdown already conveys time-to-expiry precisely; a third icon color doesn't help any user decision.

D2 — Actor ↔ model communication: pull verb + push stream

The actor exposes two surfaces to CredentialsModel: a pull verb (status(forSession:)) and a push stream (events). The model runs one long-lived Task at init that iterates the stream and re-pulls status(...) into a [String: SessionAuthStatus] cache. Views read the cache; views never touch the stream.

IdentityCenterService.swift swift 
public func status(forSession sessionName: String) async -> SessionAuthStatus

public nonisolated var events: AsyncStream<AuthEvent> { get }

public enum AuthEvent: Sendable, Hashable {
    // A1
    case signInStarted(sessionName: String)
    case signedIn(sessionName: String)
    case signInCancelled(sessionName: String)
    case signInFailed(sessionName: String)
    case signedOut(sessionName: String)

    case refreshFailed(sessionName: String)

Three sub-decisions confirmed:

  • Pattern: pull verb + push stream + single consumer. Apple precedent: NSPersistentStoreRemoteChange notifies, viewContext.fetch resolves.
  • Stream shape: nonisolated var returning one shared stream created at actor init. Matches single-consumer semantics (AsyncStream.Iterator isn't Sendable; second consumer = fatalError).
  • Event naming: operation outcomes, not status transitions. Events carry only sessionName; the model re-pulls full status. Keeps the wire format tiny and makes tests trivially state assertions about what the actor just did.

D3 — Sign-out semantics

  • Server-side POST /logout: yes, but best-effort. Per SSODeviceAuth.html §04: "Logout is best-effort. We always delete local Keychain copies regardless of whether the server call succeeds." The local purge is what must succeed; the network call is gravy.
  • Local purge scope: SSO token row only (dev.ajbeck.quorra.sso-token / <sessionName>). The OIDC client row (dev.ajbeck.quorra.oidc-client / <region>) stays — it's per-region, shared across sessions, not user-secret, and purging it punishes sibling sessions. Scope B will extend sign-out to also purge derived role-creds rows.
  • Public API: func signOut(sessionName: String) async throws. Idempotent if no row exists. Cancels any in-flight signIn for the same session before proceeding.

Order of operations inside signOut(sessionName:):

  1. If a signIn is in flight for this session, cancel it and wait for it to unwind.
  2. Read the StoredSSOToken from Keychain. If missing, emit .signedOut and return — idempotent.
  3. Emit AuthEvent.signedOut(sessionName:). UI flips immediately.
  4. Delete the SSO token Keychain row.
  5. Fire POST /logout to portal.sso.<region>.amazonaws.com with the access token as bearer.
  6. If step 5 fails: emit .signOutServerSideFailed(sessionName:). Don't throw — the user-visible state is already "signed out."

A2 decisions — silent refresh

Twelve decisions taken during the A2 design interview. Each is grounded in Apple documentation, AWS API documentation, RFC 6749, or the research docs.

D10 — Trigger model: proactive timer + lazy defensive read

Silent refresh runs from a proactive timer (T_refresh at expiresAt − 5min) and emits events via the actor's existing AsyncStream. liveToken(forSession:) additionally performs a defensive inline refresh if it's called inside the skew window or past expiry — covers cold-start with a token already inside the skew window and rare cases where T_refresh didn't fire on time. The model never sees time; it only reacts to events (preserves A1's event-driven architecture).

Rejected alternatives:

  • Proactive only. Loses the defensive guarantee that liveToken's contract — "valid for at least skew seconds" — requires for Scope B's role-cred mint path.
  • Lazy only. Sidebar icon would stay .green for hours after token went stale, because nothing triggered a status re-pull. Breaks the event-driven posture.

Apple precedent: URLCredentialStorage's renewal-window pattern (background renewal task + defensive check at point-of-use).

D11 — Two independent timers per signed-in session

One timer per job. T_refresh at expiresAt − 5min drives refresh and emits .refreshing/.refreshed/.refreshFailed. T_expire at expiresAt remains unchanged from A1 and fires .expired. On refresh success: cancel both, reschedule both for the new expiresAt. On refresh failure: leave T_expire running so .expired still fires at the original deadline — the user gets a real 5-minute grace window. When canRefresh: false, only T_expire is scheduled (A1 behavior).

Rejected alternatives:

  • Single timer at expiresAt − 5min; .expired only fires on refresh failure. Failure handler has to schedule a fresh timer at the original deadline. More branching, same end-state.
  • Single timer that does both jobs (fires .expired immediately on refresh failure). Lies to the user — token is still valid for 5 more minutes.

Apple precedent: URLSessionConfiguration.timeoutIntervalForRequest and timeoutIntervalForResource are two independent deadlines with separate jobs — they don't share a timer.

D12 — liveToken(forSession:) contract

Returns StoredSSOToken (full record — same shape signIn returns). The contract is "the returned token is valid for at least refreshSkew seconds." Single-flight via inFlightRefresh: [String: Task<StoredSSOToken, Error>].

Skew constant: ServiceConstants.refreshSkew = 5 * 60, grounded in research §09. Same skew the AWS SDKs' SSO credential provider uses, so Quorra's behavior matches AWS CLI on the same machine.

D13 — No actor-side token cache

Reaffirms A1 D6. Keychain stays the single source of truth. The App ↔ CLI architecture (CLAUDE.md: "Any mutation of AWS config/credentials files, Keychain items, or SSO tokens may happen from either binary. Both must treat the filesystem and Keychain as shared mutable state.") is load-bearing — an actor-side cache in the app would diverge from Keychain whenever the CLI refreshes or signs out, and there's no notification mechanism by design.

The hot-path cache that matters already exists at CredentialsModel.status: [String: SessionAuthStatus]. liveToken is called ~hourly per active profile (Scope B role-cred mint cadence), not per render. Keychain reads cost microseconds. The single-flight inFlightRefresh Task gives the in-memory benefit during the only window it matters — multiple callers awaiting one refresh share the in-memory result.

Terminal: emit .refreshFailed; update Keychain row to refreshToken = nil (keep accessToken and expiresAt — the access token may still be valid for minutes); cancel T_refresh; leave T_expire. Status becomes signedIn(_, canRefresh: false) until expiresAt, then expired(_, canRefresh: false) — both A1 already renders correctly.

Transient: emit .refreshFailed; don't mutate Keychain; cancel T_refresh (one-shot, no auto-retry); leave T_expire. Status stays signedIn(_, canRefresh: true). User can retry via refreshNow; next liveToken inside skew will retry inline (D12).

No auto-retry inside the skew window. The 5-minute window already is the retry window. AWS Identity Center's /token refresh doesn't issue slow_down; URLSession already does some retry at the connection layer.

D17 — case refreshing removed from SessionAuthStatus

A1 reserved case refreshing with no associated values. A2 removes it. The actor's source-of-truth status during refresh remains signedIn(expiresAt:, canRefresh:) — the session is still signed in until either refresh completes or T_expire fires. "Refreshing" is a transient activity overlay, not a session-auth state.

New model property mirrors A1's signOutFailure shape:

  • CredentialsModel.refreshingNow: Set<String> — populated on .refreshing, cleared on .refreshed/.refreshFailed. Drives the panel's "refreshing" caption and the sidebar icon's optional .pulse effect.
  • CredentialsModel.refreshFailure: Set<String> — populated on .refreshFailed, cleared on next .refreshed / new sign-in / sign-out. Drives the D16 advisory.

D18 — Refresh-token rotation per RFC 6749 §6 + §10.4

On successful refresh, build the new StoredSSOToken with refreshToken: response.refreshToken ?? old.refreshToken — replace when AWS rotates, keep old when AWS doesn't. Then overwrite the Keychain row atomically. Don't preserve the old refresh token "in case the new one is bad" — RFC 6749 §10.4 requires invalidating the old one, and keeping it for fallback enables replay if it's stolen.

D21 — Per-session async serialization via Task chain

The problem: Apple's actor only guarantees serialization between suspension points. When signOut calls await urlSession.data(for:), the actor releases its lock and a refresh task can interleave — actor reentrancy. WWDC21 "Protect mutable state with Swift actors" covers this directly.

Why Synchronization.Mutex is wrong here: Mutex.withLock is synchronous and blocking — it blocks the calling OS thread. Apple's docs and the Swift Forums concurrency thread are explicit: "You should never call blocking primitives on an actor or in async code" (WWDC21). The cooperative thread pool has ~N threads; blocking even one risks deadlock. Mutex is for synchronous multi-thread state — ours is asynchronous.

The fix: per-session async serialization via a Task chain.

IdentityCenterService+SessionLock.swift swift 
private var sessionLocks: [String: Task<Void, Never>] = [:]

private func withSessionLock<T: Sendable>(
    _ sessionName: String,
    _ body: @Sendable @escaping () async throws -> T
) async throws -> T {
    let prior = sessionLocks[sessionName]
    let work = Task<T, Error> {
        _ = await prior?.value
        return try await body()
    }
    sessionLocks[sessionName] = Task { _ = try? await work.value }
    return try await work.value
}

Every public operation on a session (signIn, signOut, internal runRefresh, refreshNow, liveToken's inline-refresh branch) wraps its body in withSessionLock. Operations on different sessions don't block each other. Operations on the same session queue and run sequentially.

Cancel-then-queue on user gestures: signOut and signIn first call inFlightRefresh[name]?.cancel() before taking the lock. URLSession honors Task cancellation — the refresh's network call unwinds quickly with CancellationError. The lock then becomes available and the user's gesture runs. User-driven actions don't wait for doomed network calls; serial semantics still hold.

This simplifies D20's scenario 10e dramatically: refresh succeeds, signOut queued behind it. Refresh writes the new token, signOut runs next and deletes it. End state: signed out. No "discard if Keychain row missing" defensive check anywhere.

apple-canonical primitiveThe Swift Forums thread on "concurrency-safe-lock" and WWDC21 both arrive at the same place: actor + Task chain for async serialization. Apple does not ship a built-in AsyncMutex; the documented pattern is what's implemented above.

B decisions — role credentials

Ten decisions taken during the B design interview. Each is grounded in Apple framework reference docs, HIG, AWS API documentation, RFC compliance, or the research docs.

D22 — Single actor, new extension files, PortalRequesting protocol seam

Role-credentials code lives on the existing IdentityCenterService actor (not a new RoleCredentialsService). New extension files mirror the A1/A2 pattern: +RoleCredentials.swift, +PortalClient.swift, +ProfileStatus.swift. Wire layer extracted as PortalRequesting protocol with a concrete PortalClient conforming, mirroring A2's OIDCRequesting/OIDCClient seam.

Why one actor, not two:

  • Sign-out atomicity. The session sign-out must purge both the SSO token row AND every derived role-cred row in one synchronized operation. With one actor + the D21 session lock, this is one withSessionLock body. With two actors, it's a cross-actor call during the lock window — exactly the actor-reentrancy hazard D21 closed.
  • Refresh interaction. Mint calls liveToken (A2) internally. Same actor means await self.liveToken(...) — A2's inFlightRefresh single-flight kicks in automatically. Two actors means a cross-boundary hop with serialized locks at both ends.

Apple-canonical precedent: AuthorizationController (AuthenticationServices) handles Apple ID, passkey, password, security key, and custom-method credentials through a single performRequest(_:) API with a discriminated ASAuthorizationResult enum. Apple splits at operations (authorize vs save vs web-auth), not at credential types. SSO tokens and role credentials are both bearer-credentials Quorra serves to consumers; they share one actor.

D23 — All three Portal verbs in PortalRequesting

AWS SSO Portal exposes ListAccounts, ListAccountRoles, GetRoleCredentials. All three land in B even though only GetRoleCredentials is load-bearing for the credentials reveal section. The discovery verbs will eventually be needed for the future profile-creation flow; adding them now means we don't revisit the wire layer later.

Pagination is handled internally — methods return flat lists, callers don't manage nextToken. Matches AWS SDK convenience patterns (e.g., the paginated() async sequences in aws-sdk-go-v2).

Skew: reuse ServiceConstants.refreshSkew = 5 * 60 from A2. Same physical value, same semantic, less surface area. Research §09 documents the 5-min figure for both SSO tokens and role credentials.

Single-flight key: "<sessionName>:<accountId>:<roleName>" — matches the Keychain row key. Concurrent liveCredentials calls for the same tuple coalesce; different tuples don't block.

No session lock around liveCredentials. Relies on three layered guarantees:

  1. inFlightMint coalesces mint-vs-mint races for the same tuple.
  2. liveToken (A2) internally takes the session lock when fetching the SSO bearer — by the time we call portal.getRoleCredentials, the bearer is fresh and the session lock has been released.
  3. Sign-out cancels every inFlightMint for the session (D27). Any in-flight mint's URLSession.data(for:) throws CancellationError; no Keychain write happens.

The alternative — taking the session lock inside liveCredentials — would deadlock because liveToken re-takes the lock. We could use Swift's #isolation macro or an isolated parameter token to bypass the deadlock, but the layered-guarantees approach gives identical end-state correctness with less complexity.

D27 — Sign-out cascade extends D3

Sign-out's existing order of operations gains a new step. The full sequence:

  1. Cancel-then-queue (extended): cancel inFlightRefresh[sessionName] and every inFlightMint[key] whose key starts with <sessionName>:, before taking the session lock.
  2. Take session lock (D21).
  3. Cancel in-flight signIn for the session (existing A1).
  4. Read the StoredSSOToken — if missing, emit .signedOut and return (idempotent).
  5. Cancel T_refresh and T_expire (existing A1).
  6. Cancel every T_mint whose key starts with <sessionName>: (new in B).
  7. Emit .signedOut(sessionName:) (UI flips immediately).
  8. Delete the SSO token Keychain row (existing A1).
  9. Enumerate role-cred rows under service: dev.ajbeck.quorra.role-creds, delete every one whose account starts with <sessionName>: (new in B).
  10. Fire Portal /logout best-effort (existing A1).
  11. If 10 fails, emit .signOutServerSideFailed (existing A1) — do NOT throw.

04D7 — Runtime edge cases

Stream consumer Task lifecycle

One Task<Void, Never> spawned in CredentialsModel.init, held in a @ObservationIgnored property, captures [weak self]. No explicit deinit cancel — when the model deallocates, the next event triggers a guard-let exit. The Task absorbs per-event failures with Never so one bad event can't take down the consumer. Not coupled to any view's lifecycle.

Sign-out partial failure surfacing

When .signOutServerSideFailed(sessionName:) fires, the model sets signOutFailure.insert(sessionName). SignInPanel's "needs action" view renders an inline advisory:

advisory copy"Local sign-out succeeded, but Quorra couldn't notify AWS. Your token will expire naturally within 8 hours."

Cleared automatically when (a) the user starts a new sign-in flow, or (b) signOut is called again successfully. No alert, no system notification — the user is already looking at the panel they just acted in; an alert would interrupt for advisory-grade information.

status(forSession:) absorbs Keychain failures

The verb doesn't throw. Mapping:

  • keychainItemMissing → .signedOut (normal "never signed in" state)
  • keychainMalformed → .signedOut + os.Logger warning
  • Any other keychainStatus → .signedOut + log

Rationale: the verb is called every sidebar render. A throw would force every caller into defensive error paths for a verb whose user-meaningful answer is always one of: signedIn, signedOut, expired, signingIn, refreshing. "Can't read the row" and "row isn't there" are visually equivalent (both mean "you need to sign in"); collapsing them to .signedOut matches user mental model.

Actor owns expiration; emits .expired events

The actor is the single centralized worker that knows ALL session-auth state transitions and emits an event for each. Listeners react; they never see time.

IdentityCenterService+Expiration.swift swift 
private var expirationTimers: [String: Task<Void, Never>] = [:]

private func scheduleExpiration(
    forSession sessionName: String,
    expiresAt: Date
) {
    expirationTimers[sessionName]?.cancel()
    let deadline = ContinuousClock.now + .seconds(expiresAt.timeIntervalSinceNow)
    expirationTimers[sessionName] = Task { [weak self] in
        do { try await Task.sleep(until: deadline, clock: .continuous) }
        catch { return }
        await self?.handleExpiration(sessionName: sessionName)
    }
}

private func handleExpiration(sessionName: String) {
    expirationTimers[sessionName] = nil
    eventContinuation.yield(.expired(sessionName: sessionName))
}

Scheduling triggers:

  • on successful signIn — schedule for the new token's expiresAt
  • on signOut — cancel
  • on first status(forSession:) after app restart — opportunistically schedule if Keychain holds a valid signed-in token but no timer exists yet
  • on A2 refresh — cancel old, schedule new for refreshed expiresAt
apple-canonical shapeTwo of Apple's own frameworks ship the same head shape: CredentialSession.eventStream: AsyncStream<CredentialSession.Event> (SecureElementCredential) and RemoteKeylessEntry…EnduringExecutionRequest.eventStream: AsyncStream<…Event> (CarKey). Apple's AsyncStream.Continuation is documented as "supports escaping" specifically to enable producers like ours that store the continuation as actor state.

Listener is pure reaction

The model's stream consumer Task receives AuthEvents and re-pulls status(forSession:) on each. No timer scheduling in the model. No Clock, no Date, no TimelineView anywhere in the UI layer. The status icon becomes a pure view that re-renders via @Observable whenever the cache updates.

Cost while signed in for 8h: one OS-coalesced wake-up at expiresAt. Zero work between sign-in and that moment.

Testing patterns (carried forward from A1/A2)

These are the established conventions for the IAM Identity Center test suite — applying them keeps the new tests internally consistent and avoids the friction patterns A2's senior review identified.

  1. Time-based timer tests go through Sleeper.sleep(until:) (D19). Production WallClockSleeper uses Task.sleep(for:). MockSleeper auto-advances synthetic time. Tests can write "schedule for now+1h, advance synthetic clock to deadline, assert event fires" using production skew values — no test-only short skews.
  2. Real-time short intervals (50–300 ms) remain valid for narrow "did this fire" assertions when the test doesn't need to advance a clock.
  3. Avoid any Clock<Duration> adoption — Swift 6.2's existential-Instant arithmetic has rough edges. Sleeper is the internally consistent seam.
  4. Prefer verb-level stubs over URL-level stubs. Use StubPortalRequesting for actor-behavior tests; reserve StubURLProtocol for wire-encoding tests (PortalClientTests). Eliminates the NSLock + nonisolated(unsafe) var friction in async-call-counting.
  5. Single-event-stream assertions via EventCollector + Swift Testing's confirmation. Events carry structural IDs only; tests assert "this case appeared" without parsing payloads.
  6. State-mutation tests > timing tests wherever possible. Most "what happens when T fires" tests can be rewritten as "what happens when handleX(...) is called directly" — no clock advance needed. Use _test_setInFlightX helpers to plant state when needed.
  7. Separate scheduling tests from action tests. Pure "is the timer dict populated" tests are tautological — drop or fold into the action test.
  8. Worst-case-payload round-trip test (D24) — guards against any silent regression at extremes (12 KB STS session token through the Keychain round-trip).
