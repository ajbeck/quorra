[SSODeviceAuth]

Quorra owns the AWS SSO device-authorization flow end-to-end: register an OIDC client, start a device-authorization grant, hand the user a browser to approve it, poll for the access token, exchange it for short-lived role credentials, and persist everything in the macOS Keychain.

// 01Overview

Quorra is a developer-machine credential manager for AWS. SSO is the most common way developers authenticate to AWS today, and the AWS CLI implements it as the OAuth 2.0 Device Authorization Grant against the AWS SSO OIDC service. Quorra implements the same flow natively in Swift so the user never has to install or shell out to the AWS CLI just to log in.

This document describes how the flow works, which AWS services are involved, the exact requests and responses Quorra makes, where state is stored, and how it is surfaced in the UI. It is the design doc for the work that lands in the SSO module of the app and the quorra-cli binary.

scopeEnd-to-end SSO sign-in for an existing IAM Identity Center start URL configured by the user. Out of scope here: provisioning the start URL itself, IAM-user long-lived keys, credential_process wiring (handled by a separate doc), and IMDS-side credential serving (also separate).

▸Flow at a glance

  1. Register — Quorra calls RegisterClient on AWS SSO OIDC and gets back a clientId and clientSecret valid for ~90 days. These are persisted in Keychain so we don't re-register on every login.
  2. Start device auth — Quorra calls StartDeviceAuthorization with the user's start URL. AWS returns a deviceCode, a userCode, a verificationUri, a verificationUriComplete, an expiresIn, and a polling interval.
  3. Open browser — Quorra opens verificationUriComplete in the user's default browser. The user signs in to their identity provider and approves the device.
  4. Poll for token — In parallel Quorra polls CreateToken with grant_type=urn:ietf:params:oauth:grant-type:device_code, respecting authorization_pending, slow_down, and the server-supplied interval. On success it gets back an accessToken, an expiresIn, and (with the sso:account:access scope) a refreshToken.
  5. List accounts & roles — Quorra calls SSO Portal's ListAccounts and ListAccountRoles to populate the in-app picker.
  6. Get role credentials — When a role is selected, Quorra calls GetRoleCredentials and returns short-lived AccessKeyId / SecretAccessKey / SessionToken / Expiration. These are what the IMDS server, credential_process, and config exporters return to consuming AWS SDKs.

▸Two AWS services

The flow touches exactly two AWS services. Both are unauthenticated for the bootstrap calls (the device flow itself does not require existing AWS credentials):

ServiceEndpoint patternWhat we call
SSO OIDCoidc.<region>.amazonaws.comRegisterClient, StartDeviceAuthorization, CreateToken
SSO Portalportal.sso.<region>.amazonaws.comListAccounts, ListAccountRoles, GetRoleCredentials, Logout

The region is the SSO instance's region — taken from the sso_region key in the user's config — not the per-profile region for AWS API calls. They are usually different.

// 02Background

▸What "AWS SSO" is, in 2026

What everyone still calls "AWS SSO" was renamed to IAM Identity Center in 2022. The protocol surface — the OIDC and Portal endpoints — kept their original sso / oidc hostnames and API shapes, so the practical flow is identical. The user-facing names changed (start URL, permission set, account assignment); the wire protocol did not.

▸Device Authorization Grant — the OAuth bit

The flow is RFC 8628 OAuth 2.0 Device Authorization Grant, with AWS-specific request and response shapes layered on top. The grant exists for clients that can't conveniently host a redirect URI — TVs, CLIs, headless tools, and desktop apps that don't want to embed a browser. The user is shown a short verification URL and (optionally) a short user code; they complete authentication on a phone or laptop browser; the device polls a token endpoint until the user finishes.

Two things make AWS's variant slightly non-vanilla:

  • Dynamic client registration. There is no pre-issued clientId. The first thing every new client does is call RegisterClient with a self-chosen clientName and an array of scopes. The response includes a clientId and clientSecret with an explicit clientSecretExpiresAt (Unix seconds, typically ~90 days out).
  • Two-stage credentials. The OIDC accessToken is not an AWS credential — you can't sign SigV4 requests with it. It's a bearer token that authorizes calls to the SSO Portal API, which in turn exchanges role assignments for short-lived AccessKeyId / SecretAccessKey / SessionToken tuples. Those are AWS credentials. The role credentials are what eventually need to land in front of the consuming SDK.

▸What the AWS CLI does today

For reference, when a user runs aws sso login --profile my-profile:

  1. It looks up the profile's sso_session (or legacy sso_start_url) in ~/.aws/config.
  2. It checks ~/.aws/sso/cache/<sha1(start_url)>.json for a cached, unexpired access token. If present, it skips the browser dance.
  3. Otherwise it walks the device-authorization flow above, opens the URL with webbrowser.open() in Python, polls until the token comes back, and writes the JSON cache file with 0o600 permissions.
  4. Subsequent SDK calls under that profile go through the AWS CLI's credentials.providers.SSOProvider, which reads the cache, calls GetRoleCredentials, and returns a refreshed credential tuple.

Quorra implements the same protocol but stores the access token and refresh token in the macOS Keychain instead of a flat JSON file, and surfaces the flow in a native UI instead of stdout.

compatQuorra still reads and writes the ~/.aws/sso/cache/*.json files in addition to its own Keychain copy, so a user running aws sso login and a user running Quorra leave the same machine in the same state for any non-Quorra tool. The Keychain is the source of truth; the JSON is a mirror written under the same lock as ~/.aws/config.

▸Glossary

TermMeaning

// 03SSO OIDC operations

Three operations on oidc.<region>.amazonaws.com. All are JSON over HTTPS, all are unauthenticated (the bootstrapping flow has, by definition, no credentials yet).

▸RegisterClient

Performs OAuth 2.0 Dynamic Client Registration. Quorra calls this once per (start URL, scope set) and caches the result for the lifetime of clientSecretExpiresAt.

RegisterClient.httphttp
POST /client/register HTTP/1.1
Host: oidc.eu-west-1.amazonaws.com
Content-Type: application/json

{
  "clientName": "quorra",
  "clientType": "public",
  "scopes": ["sso:account:access"]
}
200.jsonresponse
{
  "clientId":               "abc123...",
  "clientSecret":           "def456...",
  "clientIdIssuedAt":       1715520000,
  "clientSecretExpiresAt":  1723296000
}
Request fieldMeaning
clientNameFree-form, shown nowhere user-visible. Quorra uses literal "quorra".
clientTypeAlways "public" for desktop apps — we cannot meaningfully keep a client secret.
scopesMust include sso:account:access for the Portal API and refresh tokens.

Quorra refreshes the registration when clientSecretExpiresAt - now < 7 days to avoid the "secret expired mid-poll" race. Registration is keyed in Keychain by SSO region (the registration only works for the region it was created in).

▸StartDeviceAuthorization

Begins a device-authorization grant. Quorra calls this every time the user clicks Sign in, regardless of whether a previous access token exists.

▸CreateToken

Polled by Quorra during device flow, and also called with grant_type=refresh_token when an access token expires.

Device-code grant

CreateToken.httphttp
POST /token HTTP/1.1
Host: oidc.eu-west-1.amazonaws.com
Content-Type: application/json

{
  "clientId":     "abc123...",
  "clientSecret": "def456...",
  "grantType":    "urn:ietf:params:oauth:grant-type:device_code",
  "deviceCode":   "AAAA-very-long-opaque-string"
}
200.jsonresponse
{
  "accessToken":  "eyJ...",
  "tokenType":    "Bearer",
  "expiresIn":    28800,
  "refreshToken": "eyJ..."
}

Polling errors

Until the user finishes, CreateToken returns HTTP 400 with an error code in the body. Quorra distinguishes:

  • authorization_pending — keep polling, sleep interval seconds.
  • slow_down — increase interval by 5 seconds and keep polling.
  • expired_token — the device code is past expiresIn; restart from StartDeviceAuthorization.
  • access_denied — user clicked Deny; surface as a hard failure.
  • invalid_grant — programmer error or stale device code; surface as bug.

Refresh-token grant

CreateToken-refresh.httphttp
POST /token HTTP/1.1
Host: oidc.eu-west-1.amazonaws.com
Content-Type: application/json

{
  "clientId":     "abc123...",
  "clientSecret": "def456...",
  "grantType":    "refresh_token",
  "refreshToken": "eyJ..."
}

Refresh returns the same shape as the device grant. AWS sometimes rotates the refresh token in the response — Quorra always overwrites the stored value with whatever comes back, never re-using the old one.

retryQuorra wraps CreateToken with a deterministic poll loop driven by the server's interval. No exponential backoff beyond slow_down. The hard cap is expiresIn seconds from StartDeviceAuthorization — past that, fail and restart.

// 04SSO Portal operations

Once Quorra has an access token, it stops talking to oidc.<region> and starts talking to portal.sso.<region>. The Portal API is bearer-token authorized — every request carries an x-amz-sso_bearer_token header containing the access token.

▸GetRoleCredentials

Exchanges an account/role pair for short-lived AWS credentials. This is the call that produces something an SDK can actually sign requests with.

GetRoleCredentials.httphttp
GET /federation/credentials?role_name=AdministratorAccess&account_id=123456789012 HTTP/1.1
Host: portal.sso.eu-west-1.amazonaws.com
x-amz-sso_bearer_token: eyJ...
200.jsonresponse
{
  "roleCredentials": {
    "accessKeyId":     "ASIA...",
    "secretAccessKey": "...",
    "sessionToken":    "FwoGZXIvYXdzE...",
    "expiration":      1715548800000
  }
}

Note that expiration is milliseconds since epoch — not seconds, not ISO 8601. This trips people up. Quorra normalizes to Date (which stores seconds-since-2001 internally) at the parser boundary so nothing downstream has to remember.

▸Logout

Invalidates the access token server-side. Quorra calls this when the user explicitly signs out.

Logout.httphttp
POST /logout HTTP/1.1
Host: portal.sso.eu-west-1.amazonaws.com
x-amz-sso_bearer_token: eyJ...

Logout is best-effort. We always delete local Keychain copies regardless of whether the server call succeeds. The reverse — server-side invalidation without local cleanup — would leave a stale Keychain item lying around.

cacheQuorra caches ListAccounts/ListAccountRoles results in memory for the lifetime of the access token. Calling them every time the user expands the account picker would cost a network round-trip per click for no benefit — assignments don't change inside an 8-hour session.

// 05Browser handoff

The device-authorization flow only works because the user can complete authentication in a browser they already trust. Quorra never embeds a webview, never proxies the IdP, and never asks the user for their identity-provider credentials directly.

▸Opening the verification URL

Quorra uses NSWorkspace.shared.open(_:) to launch the user's default browser at verificationUriComplete. Since the URL already contains the user_code query parameter, the user lands on a pre-confirmed approval page and only has to click Allow.

SSOFlow.swiftswift
import AppKit

func openVerificationURL(_ url: URL) throws {
    guard NSWorkspace.shared.open(url) else {
        throw SSOError.browserLaunchFailed(url)
    }
}

▸Polling while the user is in the browser

The poll loop is independent of the browser launch. We do not wait for any callback from the browser — there is none. The browser is purely the user's interaction surface; the device polls AWS directly.

The loop is implemented as an async function that uses Task.sleep(for:) between polls. It respects cooperative cancellation, so if the user closes the sign-in sheet we stop polling and free the device code.

SSOFlow+Poll.swiftswift
func pollForToken(deviceAuth: DeviceAuthorization) async throws -> SSOAccessToken {
    var interval: Duration = .seconds(deviceAuth.interval)
    let deadline = ContinuousClock.now + .seconds(deviceAuth.expiresIn)

    while ContinuousClock.now < deadline {
        try Task.checkCancellation()
        try await Task.sleep(for: interval)

        do {
            return try await oidc.createToken(deviceAuth: deviceAuth)
        } catch SSOError.authorizationPending {
            continue
        } catch SSOError.slowDown {
            interval += .seconds(5)
        }
    }
    throw SSOError.deviceCodeExpired
}

▸Sandbox considerations

Quorra is sandboxed. Opening external URLs is allowed by default — no entitlement needed for NSWorkspace.shared.open(_:). The browser process runs entirely outside Quorra's sandbox; we hand off the URL and forget about it.

fallbackIf NSWorkspace.shared.open(_:) returns false we surface the URL and the userCode in the UI as copyable text so the user can manually paste it into a browser. This covers the rare "no default browser configured" edge case and the slightly less rare "the user is on a remote/SSH'd machine" case.

▸Why not ASWebAuthenticationSession?

ASWebAuthenticationSession is the right tool for OAuth flows that use a redirect to deliver the authorization code back to the app via a custom URL scheme. The device-authorization grant doesn't redirect anywhere — the device polls the token endpoint instead. So the framework's value (intercepting the redirect) does not apply, and using it would just give us a worse browser (no extensions, no saved passwords, no SSO cookies the user already has).

// 06AWS SDK for Swift

Quorra uses the official AWS SDK for Swift for both SSO OIDC and SSO Portal operations. We do not hand-roll JSON HTTP clients — the SDK provides typed request/response models, retry policy, signing (where needed), and consistent error handling, all maintained by AWS.

▸Why the SDK

  • Typed models. RegisterClientInput, StartDeviceAuthorizationOutput, etc. are real Swift types with correctly-named fields. No string-keyed dictionaries.
  • Error mapping. Polling errors (AuthorizationPendingException, SlowDownException, ExpiredTokenException) come back as distinct typed exceptions we can catch by type, not parsed strings.
  • Retry & signing. The Portal API uses bearer-token auth (no SigV4), but the SDK still handles connection reuse, timeouts, and retry on 5xx for us.
  • Future-proof. When AWS adds new fields or endpoints (as they have repeatedly with SSO since 2019), an swift package update picks them up.

▸Package dependencies

Two SDK products, added as Swift Package dependencies on the app and CLI targets:

Package.swiftswift
.package(
    url: "https://github.com/awslabs/aws-sdk-swift.git",
    from: "1.0.0"
),

// In each target.dependencies:
.product(name: "AWSSSOOIDC", package: "aws-sdk-swift"),
.product(name: "AWSSSO",     package: "aws-sdk-swift"),

We deliberately do not depend on AWSClientRuntime or ClientRuntime directly — those come transitively. We also do not depend on any other service SDK at this layer (no STS, no IAM). Quorra's own consumers use the credentials Quorra produces; they can pull in whatever service SDKs they want.

▸SSOOIDCClient

One client per SSO region. Constructed with no credentials — every operation we call is unauthenticated except CreateToken with a refresh token, which AWS treats as the "credential" for that one call.

SSOOIDCClient.swiftswift
import AWSSSOOIDC

let oidc = try SSOOIDCClient(region: ssoRegion)

// RegisterClient
let reg = try await oidc.registerClient(input: .init(
    clientName: "quorra",
    clientType: "public",
    scopes:     ["sso:account:access"]
))

// StartDeviceAuthorization
let dev = try await oidc.startDeviceAuthorization(input: .init(
    clientId:     reg.clientId,
    clientSecret: reg.clientSecret,
    startUrl:     startURL.absoluteString
))

// CreateToken (device code)
let tok = try await oidc.createToken(input: .init(
    clientId:     reg.clientId,
    clientSecret: reg.clientSecret,
    deviceCode:   dev.deviceCode,
    grantType:    "urn:ietf:params:oauth:grant-type:device_code"
))

Polling-error mapping

The SDK throws typed exceptions per AWS error code. Quorra maps them to its own SSOError enum so the rest of the app doesn't depend on SDK types:

SSOError+SDK.swiftswift
do {
    let tok = try await oidc.createToken(input: input)
    return tok
} catch let e as AuthorizationPendingException {
    throw SSOError.authorizationPending
} catch let e as SlowDownException {
    throw SSOError.slowDown
} catch let e as ExpiredTokenException {
    throw SSOError.deviceCodeExpired
} catch let e as AccessDeniedException {
    throw SSOError.userDenied
} catch {
    throw SSOError.transport(error)
}

Same shape, different module: AWSSSO. One client per region. The bearer token is passed per-call, not per-client, so we don't reconstruct the client when the token rotates.

▸Pagination

Both ListAccounts and ListAccountRoles are paginated. The SDK exposes paginated APIs as AsyncSequences; Quorra wraps them in helpers that collect into [SSOAccount] / [SSORole] arrays. The full list almost always fits in one page (very few orgs have >100 accounts assigned to one user), but the helper handles the multi-page case for free.

▸Module boundary

Only one Swift type — SSOService — actually imports AWSSSOOIDC and AWSSSO. Everything else in Quorra talks to SSOService through plain Swift value types (SSOAccount, SSORole, SSORoleCredentials, SSOAccessToken). This keeps the SDK as a leaf dependency, makes SSOService easy to mock for tests, and means an SDK breaking-change ripples through one file, not the whole app.

versioningThe AWS SDK for Swift hit 1.0 in 2024 and follows semver. We pin to from: "1.0.0", accepting minor and patch updates automatically and gating major bumps behind a manual review.

// 07Keychain schema

Quorra stores three classes of secret in the macOS Keychain. All items live in the shared access group $(AppIdentifierPrefix)dev.ajbeck.quorra.shared so the app and the CLI both read and write them. Accessibility is kSecAttrAccessibleWhenUnlockedThisDeviceOnly — credentials never leave this Mac via iCloud Keychain sync.

▸Item types

Itemserviceaccountgeneric data (JSON)
Client registration dev.ajbeck.quorra.sso.client <sso_region> { clientId, clientSecret, issuedAt, expiresAt }
Access & refresh tokens dev.ajbeck.quorra.sso.token <start_url> { accessToken, refreshToken, region, registrationScopes, startUrl, expiresAt }
Role credentials cache dev.ajbeck.quorra.sso.role <account_id>:<role_name>:<start_url> { accessKeyId, secretAccessKey, sessionToken, expiration }

▸Why three items, not one

Three different lifetimes, three different cache keys, three different consumers:

  • Client registration rotates every ~90 days, is keyed by region, and is shared across every start URL in that region.
  • Tokens rotate every 8 hours (access) / 90 days (refresh), are keyed by start URL, and are shared across every account/role under that start URL.
  • Role credentials rotate every hour, are keyed by account+role+start_url, and are consumed by IMDS / credential_process / config exporters.

▸Item shape

Quorra wraps every Keychain item in the same Swift type: KeychainItem<Payload: Codable>. The payload is JSON-encoded into the item's kSecValueData. Metadata (region, start URL, account ID) lives in kSecAttrAccount / kSecAttrService so a Keychain Access listing shows enough to identify each item without decrypting it.

KeychainSchema.swiftswift
struct SSOClientRegistration: Codable {
    let clientId:     String
    let clientSecret: String
    let issuedAt:     Date
    let expiresAt:    Date
    let scopes:       [String]
}

struct SSOAccessToken: Codable {
    let accessToken:        String
    let refreshToken:       String?
    let startUrl:           URL
    let region:             String
    let registrationScopes: [String]
    let expiresAt:          Date
}

struct SSORoleCredentials: Codable {
    let accessKeyId:     String
    let secretAccessKey: String
    let sessionToken:    String
    let expiration:      Date
    let accountId:       String
    let roleName:        String
    let startUrl:        URL
}

▸Mirror: ~/.aws/sso/cache

For ecosystem compatibility, every time Quorra writes a token to Keychain it also writes ~/.aws/sso/cache/<sha1(start_url)>.json with the AWS-CLI-compatible shape. The fields and naming are dictated by AWS — we mirror, we don't invent.

cache-file.jsonaws-cli mirror
{
  "startUrl":           "https://my-org.awsapps.com/start",
  "region":             "eu-west-1",
  "accessToken":        "eyJ...",
  "expiresAt":          "2026-05-12T20:00:00Z",
  "clientId":           "abc123...",
  "clientSecret":       "def456...",
  "registrationExpiresAt": "2026-08-10T00:00:00Z",
  "refreshToken":       "eyJ..."
}

The mirror file is written through the same fcntl-locked I/O path as ~/.aws/config, with mode 0o600. The Keychain copy is the source of truth — if the two ever disagree, Quorra trusts Keychain and rewrites the file.

secret disciplineThe role-credentials Keychain item is technically an optimization — given a fresh access token we can always re-derive role credentials by calling GetRoleCredentials. We cache them anyway because IMDS clients hit us on a hot path and can't tolerate an extra Portal API round-trip on every request. The cache is invalidated 5 minutes before expiration to leave headroom.

// 08UI design

SSO sign-in is presented as a sheet attached to the main window, not a separate window. Sheets feel like a transient task — the user starts a flow, completes it, and returns to where they were. SwiftUI's .sheet(isPresented:) with a custom SSOSignInView is the surface.

▸States

The sheet is a finite state machine driven by an @Observable model:

SSOSignInModel.swiftswift
@Observable
final class SSOSignInModel {
    enum Phase {
        case idle
        case registering
        case awaitingApproval(DeviceAuthorization)
        case signedIn(SSOAccessToken)
        case failed(SSOError)
    }
    private(set) var phase: Phase = .idle
}

▸Idle

Default. Shows the SSO session name, the start URL, and a single Sign in button. Below the button, a faint description: "Quorra will open your default browser. Approve the request to continue."

▸Registering

Brief — usually under a second. Shows a spinner with the label "Registering with AWS…". This phase is skipped if a valid client registration is already cached.

▸Awaiting approval

The sheet's primary state during the flow. The browser has been launched. The sheet shows:

  • A large monospaced render of the user code (WDJB-MJHT) with a Copy button.
  • The verification URL as copyable text, with an Open in Browser button next to it (in case the auto-open failed).
  • A countdown timer: "Code expires in 9:42", derived from expiresIn.
  • A Cancel button which cancels the polling task.

▸Signed in

Shown for 1 second then dismissed automatically. A green check, the start URL, the user's email (from the first ListAccounts result), and an OK button for users who want to dismiss explicitly.

▸Failed

Error-specific copy. The two cases worth dedicated copy are:

  • User denied. "You declined the sign-in request in your browser. Try again, or close this sheet."
  • Code expired. "The sign-in code expired before it was approved. Click Sign in to start again."

Everything else falls back to a generic error with the underlying message in a disclosure triangle.

▸Settings

The Settings window grows an SSO tab listing all configured SSO sessions. Each session shows its start URL, region, scopes, registration expiry, last sign-in time, and a Sign out button that calls Logout and deletes the local Keychain copies.

// 09Implementation phases

SSO ships in five phases. Each phase is independently mergeable and adds a visible capability to the app. None of them touches IMDS or credential_process wiring — those live in their own plans and consume the credentials this work produces.

  1. Phase 1 — package wiring & SDK clients

    Add aws-sdk-swift as a Swift Package dependency. Add AWSSSOOIDC and AWSSSO products to the app and CLI targets. Build green on both targets. Wire one no-op call (e.g., construct an SSOOIDCClient for eu-west-1) to verify imports and entitlements. Tests: build success.

  2. Phase 2 — Keychain schema & helpers

    Implement KeychainItem<Payload> wrapper, the three concrete payload types, and the access-group plumbing. Add a CLI subcommand quorra-cli keychain dump for dev visibility. Tests: round-trip save/load/delete in a test access group; isolation between regions and start URLs.

  3. Phase 3 — OIDC flow (no UI)

    Implement SSOService with register(), startDeviceAuthorization(), pollForToken(deviceAuth:), and refresh(token:). Wire the polling loop. Map SDK exceptions to SSOError. Add an integration-test target gated behind an SSO_INTEGRATION=1 environment variable that runs the live flow against a real start URL. Tests: unit tests for error mapping with mocked clients.

  4. Phase 4 — Portal flow + role credential cache

    Implement listAccounts(), listAccountRoles(accountId:), getRoleCredentials(accountId:roleName:), and the role-credentials Keychain cache. Add the ~/.aws/sso/cache mirror writer behind the existing fcntl lock. Tests: paginated list helpers; cache invalidation 5 minutes before expiration; mirror file written atomically.

  5. Phase 5 — UI & settings

    Add SSOSignInView sheet driven by SSOSignInModel. Wire to the main window. Populate the sidebar tree from cached ListAccounts/ListAccountRoles output. Add the Settings → SSO tab with sign-out. Tests: #Previews for every phase of the sheet.

▸Phases out of scope

  • Menu-bar role switcher — future, after Phase 5 has shipped and we have real usage data.
  • SSO start-URL provisioning — Quorra will, in a later doc, walk users through entering a new start URL. For now we read whatever the user has already configured in ~/.aws/config.
  • Sub-account assume-role chains — role_arn/source_profile support is its own design; SSO + STS chains are the most common combo and will share the credential pipeline once both are independently solid.

// 10Decisions

●device flow, not auth-code ●aws-sdk-swift, not hand-rolled http ●nsworkspace, not aswebauthsession ●keychain primary, json mirror ●three keychain items, not one ●cache role credentials ●refresh tokens always rotated ●per-region oidc client

▸Device authorization grant, not authorization-code

The auth-code flow with PKCE would require a redirect URI. Desktop apps can register custom URL schemes but the UX (browser → switch to app via scheme) is consistently buggier than the device-code flow's "leave the browser open, come back when ready" pattern. The AWS CLI also uses device flow, so we get protocol parity with the most common other client for free.

▸AWS SDK for Swift, not hand-rolled HTTP

The OIDC and Portal APIs are small enough that we could hand-roll them — but only if we also wanted to hand-roll error mapping, retry, connection reuse, and ongoing maintenance for AWS API additions. The SDK is a leaf dependency on one Swift file in our codebase; that is cheap. A custom HTTP layer would be expensive to keep correct.

▸NSWorkspace, not ASWebAuthenticationSession

Already covered in Browser handoff. The TL;DR: ASWebAuthenticationSession exists to capture redirect URIs, which the device flow doesn't use. Using the user's actual default browser also reuses any IdP session cookies they already have, which is a much smoother UX.

▸Keychain as source of truth, JSON as mirror

The Keychain has access control, hardware-backed protection, and survives app reinstalls. JSON files don't. But ecosystem tools (the AWS CLI, the AWS SDKs in other languages, third-party tools) only know how to read the JSON cache. So Keychain is canonical, and we write the JSON as a derived view of it. If they ever disagree (e.g. the user wiped ~/.aws/sso/cache manually), Keychain wins and we rewrite the JSON.

▸Three Keychain items, not one bundle

One bundle would be simpler to read but conflates three different secret lifetimes. Splitting them lets us delete role credentials independently of the access token, rotate the access token without rewriting the registration, and identify items at a glance in Keychain Access without decrypting them. The cost — three round-trips on a cold sign-in — is paid once per 8 hours.

▸Cache role credentials

Strictly speaking, role credentials are derived data. We could re-derive them on every call to GetRoleCredentials and never store them. We don't, because the IMDS server has to respond to credential requests in milliseconds and a Portal API round-trip on every request would blow that budget. The cache is invalidated 5 minutes before expiration; the trade-off is an at-most-five-minute window of staleness, which is well within AWS's clock-skew tolerance for SigV4.

▸Refresh tokens always rotated

AWS sometimes returns a new refresh token on a refresh call, sometimes returns the same one. Quorra always overwrites the stored value with whatever the response contains, even if it's identical. Treating "the response is the new state" as a uniform rule eliminates a class of "did it rotate?" bugs.

▸Per-region OIDC client

An SSOOIDCClient is bound to a region at construction time. Quorra builds one per sso_region seen in ~/.aws/config and caches them for the app's lifetime. Cheap to create, but reusing them lets HTTP/2 connection pooling kick in across multiple sign-ins.

▸What we considered and rejected

  • Embedded WKWebView for sign-in. Rejected: defeats the user's password manager, breaks SSO cookies, and gives Quorra access to credentials it has no business seeing.
  • Storing tokens in UserDefaults instead of Keychain. Rejected: UserDefaults is plaintext, world-readable for any process that can attach to our container, and not encrypted at rest in any meaningful sense.
  • Skipping the JSON mirror. Rejected: breaks aws sso login interop and any consumer that goes through the AWS CLI's credential provider chain. The compatibility cost of writing the file is trivial.
  • Polling on a fixed 5s interval. Rejected: AWS reserves the right to ask us to slow down, and ignoring slow_down is the fastest way to get a client throttled.
