A working memo on how to lay out the Quorra repository, the Xcode project navigator, and the target graph — for an app, a CLI, and the shared modules that bind them. Aimed at a structure that survives sandboxing, App Store distribution, and a long second act as the codebase grows.

▌ Recommendations · The Short Version

Six decisions, in order of how much they save you.

  1. Keep synchronized folders. Quorra already uses Xcode 16 PBXFileSystemSynchronizedRootGroup — do not regress to virtual groups.
  2. Adopt a single workspace (Quorra.xcworkspace) that contains the .xcodeproj plus local Swift packages — the shared boundary between app and CLI.
  3. Move shared logic into local SwiftPM packages under Packages/. Make QuorraCore the umbrella; AWSConfigINI is the first leaf.
  4. Three Xcode targets, one workspace: Quorra (app), quorra-cli (CLI), QuorraTests (UI/integration). Library/unit tests ride inside the SwiftPM package.
  5. Rename quorra/ → App/ on disk and update the synchronized folder. The lower-case Mac-target name is implementation detail; App/ reads as architecture.
  6. Fix the typo: project.pbxproj currently references ../Pacakges/INI. The folder doesn't exist; the package isn't really wired in yet.

§ 01

Repository folders, on disk.

The thing your shell, your `git` and your future self all see

Quorra is small now and will grow into something with multiple deliverables — an app, a CLI, several modules, possibly a Homebrew formula and a launchd plist — that all need a place. The right tree is conservative at the root, expressive one level down, and tells a stranger which directory contains the executable, which contains the libraries, and which contains tests.

§ 02

Folders vs Groups, decisively.

The Xcode 16 answer is folders. Here's the texture.

Xcode has two ways to represent a directory in the Project navigator. Groups are the classic yellow folders — a virtual collection that lives inside project.pbxproj and may or may not match disk. Folders (called synchronized folders or buildable folders since Xcode 16) are blue — they reference an actual filesystem directory and Xcode automatically picks up files inside them, no pbxproj edit required.

For a single-developer project with a long horizon and a CLI sibling that will share files via SwiftPM packages, the decision is one-sided: folders, everywhere. The pbxproj file should describe targets and build settings — not enumerate every .swift file you ever add.

Folders (blue)

PBXFileSystemSynchronizedRootGroup
  • Xcode auto-picks up new files. Add a .swift in Finder, it appears in the navigator at next focus.
  • Tiny pbxproj footprint — the project file records the directory path, not its enumeration.
  • Near-zero merge conflicts in project.pbxproj when files are added or removed.
  • Filesystem and project navigator are guaranteed to agree — no drift, no “red” missing files.
  • Xcode 16's default for new projects. Already in use here for quorra/ and quorraTests/.
  • Per-file membership exceptions (e.g. this one file is iOS-only) require an exception list — fine for rare cases, awkward at scale.
  • Less control over navigator order — folder contents are sorted by Xcode, not by pbxproj order.
Verdict — Default. Use for everything in this project.

Groups (yellow)

PBXGroup
  • Navigator structure can diverge from disk — useful if you need a curated view that doesn't match the filesystem.
  • Per-file target membership is granular and explicit.
  • Manual control over file order in the navigator.
  • Every file add/remove edits project.pbxproj. On a team, this is the #1 source of merge conflicts.
  • Files can go missing (red in navigator) without anyone noticing — disk and project drift apart.
  • Two sources of truth (disk + pbxproj), both wrong in interesting ways.
  • Apple's own docs lead with folders as the recommended path.
Verdict — Reserve for rare exceptions; keep one Packages group at most.

The one place a group still earns its keep

Apple's own guidance for adding a local Swift package to a project says: “Place the package in a Packages group to make it easier to track” [3]. Local packages live as folder references inside the project, but a group is a fine container around them — it lets you collect QuorraCore alongside any future packages without forcing them to share a parent directory on disk that has no semantic meaning. This is the only group I'd keep.

§ 03

Target organization.

Three Xcode targets, one SwiftPM package, one workspace

The interesting tension in Quorra is that the app and the CLI are independent binaries that share state only via Keychain (per CLAUDE.md). They cannot rely on bundle resources passed between processes. The shared surface must therefore be code, compiled into both — exactly what a SwiftPM library product is good at. A library does not impose a runtime relationship; it just gives both binaries the same QuorraKeychain.swift, the same AWSConfigINI, and the same access-group constants.

Why the CLI is its own Xcode target, not a SwiftPM executable product

SwiftPM happily produces executables — the .executableTarget kind is exactly that. But a sandboxed-app sibling that needs keychain-access-groups entitlements, code-signing under the same Team ID, and a stable bundle identifier (dev.ajbeck.quorra.cli) is much easier to manage as an Xcode target than as a SwiftPM executable product. Xcode handles signing, entitlements, and provisioning per-target through its UI; SwiftPM does not [4]. The CLI links SwiftPM library products, but it is an Xcode target.

“When you organize your app's codebase using local packages, your Swift package's code is part of the same repository as your app's code. As you create more apps, consider moving local packages to their own Git repositories…” Apple Developer Documentation — Organizing your code with local packages [2]

Test target placement — the rule of thumb

Library tests follow the library. Tests for AWSConfigINI, QuorraKeychain, BookmarkStorage-style logic, etc. all live in Packages/QuorraCore/Tests/. They run via swift test or the package's auto-generated scheme — no Xcode .app required, no UserDefaults pollution. The existing BookmarkStorageTests should move into the package the moment BookmarkStorage moves into QuorraSupport.

The Xcode-only test target (QuorraAppTests, formerly quorraTests) is reserved for tests that genuinely need the app target — anything that exercises AppModel wiring, the security-scoped bookmark resolution against a real container, or eventual UI tests. Per Apple's testing docs, Swift Testing and XCTest can coexist in the same target [5].

One Package.swift, several library products

The package manifest is the single source of truth for what the app and the CLI can import. Keeping all shared modules in one package (rather than one package per module) means one Package.swift to maintain, fast cross-module compilation, and a single point at which to declare the macOS(.v26) floor.

// swift-tools-version: 6.2
import PackageDescription

let package = Package(
    name: "QuorraCore",
    platforms: [.macOS(.v26)],
    products: [
        .library(name: "AWSConfigINI",    targets: ["AWSConfigINI"]),
        .library(name: "AWSConfig",       targets: ["AWSConfig"]),
        .library(name: "QuorraKeychain",  targets: ["QuorraKeychain"]),
        .library(name: "QuorraIMDS",      targets: ["QuorraIMDS"]),
        .library(name: "QuorraSSO",       targets: ["QuorraSSO"]),
        .library(name: "QuorraSupport",   targets: ["QuorraSupport"]),
    ],
    targets: [
        .target(name: "AWSConfigINI"),
        .target(name: "AWSConfig",      dependencies: ["AWSConfigINI", "QuorraSupport"]),
        .target(name: "QuorraKeychain", dependencies: ["QuorraSupport"]),
        .target(name: "QuorraIMDS",     dependencies: ["QuorraKeychain", "QuorraSupport"]),
        .target(name: "QuorraSSO",      dependencies: ["QuorraKeychain", "QuorraSupport"]),
        .target(name: "QuorraSupport"),

        .testTarget(name: "AWSConfigINITests",    dependencies: ["AWSConfigINI"]),
        .testTarget(name: "AWSConfigTests",       dependencies: ["AWSConfig"]),
        .testTarget(name: "QuorraKeychainTests",  dependencies: ["QuorraKeychain"]),
        .testTarget(name: "QuorraIMDSTests",      dependencies: ["QuorraIMDS"]),
        .testTarget(name: "QuorraSSOTests",       dependencies: ["QuorraSSO"]),
        .testTarget(name: "QuorraSupportTests",   dependencies: ["QuorraSupport"]),
    ]
)
§ 05

Open questions.

Decisions a human should make before any of this lands
  1. Workspace or no workspace? A workspace adds one file at the root and is the canonical way to combine an .xcodeproj with local Swift packages. The alternative is to keep the package as a folder reference inside the .xcodeproj. Workspaces feel slightly more correct for App + CLI + Package; folder reference is one fewer file. Either works.
  2. Does the CLI ship inside the app bundle, or as a separate binary? CLAUDE.md leans toward independent binaries. If the app ever needs to “install” the CLI for the user, Apple's Embedding a command-line tool in a sandboxed app guide [6] is the prescribed path — but that's a different topology to the one above. Worth confirming.
  3. One package or several? Single QuorraCore package with many library targets is what's drawn here. The alternative is one package per concern (AWSConfigINI/, QuorraKeychain/, …). Several packages are easier to extract publicly later but heavier today.
  4. Rename quorra/ to App/? Ergonomically nicer; mechanically a one-line pbxproj edit on the synchronized folder path. But it breaks any in-flight branches that still reference quorra/. A merge-window decision.
  5. Where does the sandbox-free CLI's entitlement file live? Same folder as the source (CLI/QuorraCLI.entitlements) is the lazy answer. A dedicated Configs/ sibling is the tidy answer. Pick one and be consistent.
  6. The ../Pacakges/INI typo. Was the INI module ever working in Xcode, or is this an aspirational stub? Affects whether the migration is a refactor or a fresh start.
