A working memo on how the Quorra repository, the Xcode project navigator, and the target graph are laid out — for an app, a CLI, and the shared modules that bind them. The structure is built to survive sandboxing, Homebrew Cask distribution today, and an App Store upload tomorrow as the codebase grows.

▌ Decisions · The Short Version

Six decisions, in order of how much they save you.

  1. Synchronized folders, everywhere. Quorra uses Xcode 26 PBXFileSystemSynchronizedRootGroup for every source root — no virtual groups outside the workspace's package container.
  2. One workspace (Quorra.xcworkspace) that owns the .xcodeproj plus the local QuorraCore Swift package — the shared boundary between app and CLI.
  3. Shared logic lives in a local SwiftPM package under Packages/QuorraCore/. AWSConfigINI is the first leaf; more libraries (AWSConfig, QuorraKeychain, QuorraIMDS, QuorraSSO) join it as features land.
  4. Three Xcode targets: quorra (app, sandboxed), quorra-cli (CLI, sandboxed), quorraTests (Swift Testing). Library tests ride inside the SwiftPM package.
  5. Folder name = target name = binary name. Source roots are App/ and quorra-cli/ on disk. Symmetry was tempting (App/ + CLI/) but discoverability and avoiding a synchronized-folder rename won out.
  6. Distribution: Homebrew Cask now, App Store-ready by construction. The CLI is embedded inside Quorra.app/Contents/MacOS/quorra-cli and a symlink installer puts it on $PATH. Sandbox + hardened runtime + identifier-based signing make App Store distribution a channel flip, not a rebuild.

§ 01

Repository folders, on disk.

The thing your shell, your `git` and your future self all see

Quorra is small now and will grow into something with multiple deliverables — an app, a CLI, several modules, a Homebrew Cask formula, eventually an App Store submission — that all need a place. The tree is conservative at the root, expressive one level down, and tells a stranger which directory contains the executable, which contains the libraries, and which contains tests.

Why quorra-cli/ and not CLI/

An earlier draft of this report proposed renaming the CLI source folder to CLI/ for symmetry with App/. That was reversed. Folder name = target name = binary name beats symmetry: a stranger landing in the repo can read off quorra-cli/ and know exactly what binary will fall out of it. Renaming a synchronized folder is also a high-touch operation in pbxproj; the win wasn't worth the churn.

“Folders have a much smaller representation in the project file, which can result in fewer merge conflicts because when you add or remove files to the project you don't modify the project file.” Apple Developer Documentation — Managing files and folders [1]
§ 02

Folders vs Groups, decisively.

The Xcode 26 answer is folders. Here's the texture.

Xcode has two ways to represent a directory in the Project navigator. Groups are the classic yellow folders — a virtual collection that lives inside project.pbxproj and may or may not match disk. Folders (called synchronized folders or buildable folders, available in Xcode 16 and later (shipping with Xcode 26 here)) are blue — they reference an actual filesystem directory and Xcode automatically picks up files inside them, no pbxproj edit required.

For a single-developer project with a long horizon and a CLI sibling that will share files via SwiftPM packages, the decision is one-sided: folders, everywhere. The pbxproj file should describe targets and build settings — not enumerate every .swift file you ever add.

Folders (blue)

PBXFileSystemSynchronizedRootGroup
  • Xcode auto-picks up new files. Add a .swift in Finder, it appears in the navigator at next focus.
  • Tiny pbxproj footprint — the project file records the directory path, not its enumeration.
  • Near-zero merge conflicts in project.pbxproj when files are added or removed.
  • Filesystem and project navigator are guaranteed to agree — no drift, no “red” missing files.
  • Xcode's default for new projects since Xcode 16; shipping in Xcode 26. In use here for App/, quorra-cli/, and Tests/QuorraAppTests/.
  • Per-file membership exceptions (e.g. this one file is iOS-only) require an exception list — fine for rare cases, awkward at scale.
  • Less control over navigator order — folder contents are sorted by Xcode, not by pbxproj order.
Verdict — Default. Use for everything in this project.

Groups (yellow)

PBXGroup
  • Navigator structure can diverge from disk — useful if you need a curated view that doesn't match the filesystem.
  • Per-file target membership is granular and explicit.
  • Manual control over file order in the navigator.
  • Every file add/remove edits project.pbxproj. On a team, this is the #1 source of merge conflicts.
  • Files can go missing (red in navigator) without anyone noticing — disk and project drift apart.
  • Two sources of truth (disk + pbxproj), both wrong in interesting ways.
  • Apple's own docs lead with folders as the recommended path.
Verdict — Reserve for rare exceptions; keep one Packages group at most.

The one place a group still earns its keep

Apple's own guidance for adding a local Swift package to a project says: “Place the package in a Packages group to make it easier to track” [3]. Local packages live as folder references inside the workspace, but a group is a fine container around them — it lets us collect QuorraCore alongside any future packages without forcing them to share a parent directory on disk that has no semantic meaning. This is the only group we keep.

§ 03

Target organization.

Three Xcode targets, one SwiftPM package, one workspace

The interesting tension in Quorra is that the app and the CLI are independent binaries that share state only via Keychain (per CLAUDE.md). They cannot rely on bundle resources passed between processes. The shared surface must therefore be code, compiled into both — exactly what a SwiftPM library product is good at. A library does not impose a runtime relationship; it just gives both binaries the same AWSConfigINI, the same QuorraKeychain, and the same access-group constants.

Entitlements — both binaries, identical set

App and CLI share the same four entitlements. The CLI is sandboxed too — Mac App Store distribution is the long-term plan and a non-sandboxed sibling would block it.

com.apple.security.app-sandbox                       = true
com.apple.security.files.user-selected.read-write     = true
com.apple.security.network.client                    = true
keychain-access-groups                               = [ $(AppIdentifierPrefix)dev.ajbeck.quorra.shared ]

# Explicitly NOT used:
# com.apple.security.inherit — the CLI is never spawned as a child of the app.
# AWS SDKs and shells exec the CLI directly, so it must stand on its own entitlements.

Embedding the CLI in the app bundle

The CLI is copied into the app via a Copy Files build phase (destination: Executables), with Code Sign On Copy enabled and a target dependency from quorra on quorra-cli. End result: Quorra.app/Contents/MacOS/quorra-cli is signed with the same Team ID as the app, ships with it, and is discoverable from the app via Bundle.main.bundleURL. Tools/install-cli.sh creates a symlink at ~/.local/bin/quorra-cli pointing to that path so users get the CLI on their $PATH without us copying anything outside the bundle.

Why the CLI is its own Xcode target, not a SwiftPM executable product

SwiftPM happily produces executables — the .executableTarget kind is exactly that. But a sandboxed sibling that needs keychain-access-groups entitlements, code-signing under the same Team ID, and a stable bundle identifier (dev.ajbeck.quorra.cli) is much easier to manage as an Xcode target than as a SwiftPM executable. Xcode handles signing, entitlements, and provisioning per-target through its UI; SwiftPM does not [4]. The CLI links SwiftPM library products, but it is an Xcode target.

“When you organize your app's codebase using local packages, your Swift package's code is part of the same repository as your app's code. As you create more apps, consider moving local packages to their own Git repositories…” Apple Developer Documentation — Organizing your code with local packages [2]

Test target placement — the rule of thumb

Library tests follow the library. Tests for AWSConfigINI, QuorraKeychain, BookmarkStorage-style logic, etc. all live in Packages/QuorraCore/Tests/. They run via swift test or the package's auto-generated scheme — no Xcode .app required, no UserDefaults pollution. The existing BookmarkStorageTests moves into the package the moment BookmarkStorage moves into a library target there.

The Xcode-only test target (quorraTests, sources at Tests/QuorraAppTests/) is reserved for tests that genuinely need the app target — anything that exercises AppModel wiring, the security-scoped bookmark resolution against a real container, or eventual UI tests. Per Apple's testing docs, Swift Testing and XCTest can coexist in the same target [5].

One Package.swift, growing list of library products

The package manifest is the single source of truth for what the app and the CLI can import. Keeping all shared modules in one package (rather than one package per module) means one Package.swift to maintain, fast cross-module compilation, and a single point at which to declare the macOS(.v26) floor. AWSConfigINI is the leaf shipping today; the other libraries below are sketched in for when their concerns land.

// swift-tools-version: 6.2
import PackageDescription

let package = Package(
    name: "QuorraCore",
    platforms: [.macOS(.v26)],
    products: [
        .library(name: "AWSConfigINI",    targets: ["AWSConfigINI"]),     // shipping
        // .library(name: "AWSConfig",       targets: ["AWSConfig"]),       // future
        // .library(name: "QuorraKeychain",  targets: ["QuorraKeychain"]),  // future
        // .library(name: "QuorraIMDS",      targets: ["QuorraIMDS"]),      // future
        // .library(name: "QuorraSSO",       targets: ["QuorraSSO"]),       // future
        // .library(name: "QuorraSupport",   targets: ["QuorraSupport"]),   // future
    ],
    targets: [
        .target(name: "AWSConfigINI"),
        .testTarget(name: "AWSConfigINITests", dependencies: ["AWSConfigINI"]),
    ]
)
§ 05

Distribution.

Homebrew Cask now · App Store-ready by construction

Quorra ships through Homebrew Cask first. The user installs Quorra.app; the CLI rides inside it at Quorra.app/Contents/MacOS/quorra-cli; Tools/install-cli.sh drops a symlink at ~/.local/bin/quorra-cli so the CLI ends up on $PATH. There is no second installer to maintain, no separate signing pipeline for the CLI, and no place where the app and CLI binaries can drift out of sync — they are built and signed together.

Why this works for both channels

The structural choices that the previous sections describe — sandboxing on both binaries, hardened runtime, identifier-based code signing, the embedded CLI, the shared Keychain access group — are exactly the choices required for App Store submission. Switching distribution channels is therefore an upload-target change, not a rebuild:

ConcernHomebrew Cask (today)Mac App Store (later)
BinaryQuorra.app with embedded quorra-cliSame Quorra.app, same embedded CLI
SandboxingRequired by usRequired by App Review
Hardened runtimeRequired for notarizationRequired by App Review
Code signingDeveloper ID ApplicationApple Distribution + identifier-based profile
CLI on $PATHinstall-cli.sh symlinks into ~/.local/binSame script, run from the app's first-launch flow
Keychain group$(AppIdentifierPrefix)dev.ajbeck.quorra.sharedIdentical

The only thing that changes between channels is the signing certificate and the upload destination. Mac App Store is the long-term plan; Homebrew Cask is the right entry point for a developer-tool audience that already lives in brew.

§ 06

Decisions made.

The questions the earlier draft of this report left open — now answered
  1. Workspace. Quorra.xcworkspace is the front door — it owns quorra.xcodeproj and Packages/QuorraCore. The pbxproj uses XCSwiftPackageProductDependency entries; there is no XCLocalSwiftPackageReference. Workspace-as-truth keeps schemes and package resolution coherent across app and CLI.
  2. The CLI ships inside the app bundle. Embedded at Quorra.app/Contents/MacOS/quorra-cli via a Copy Files (Executables) build phase with Code Sign On Copy. Tools/install-cli.sh symlinks ~/.local/bin/quorra-cli to the bundle path so users get it on $PATH. Apple's Embedding a command-line tool in a sandboxed app guide [6] is the model.
  3. One package, growing. Single QuorraCore package with many library targets, added as features land. AWSConfigINI ships today; AWSConfig, QuorraKeychain, QuorraIMDS, QuorraSSO, QuorraSupport follow.
  4. App source folder is App/; CLI source folder is quorra-cli/. The CLI was deliberately not renamed to CLI/: folder name = target name = binary name beats symmetry, and skipping a synchronized-folder rename avoided a high-risk pbxproj operation.
  5. Entitlements live in Configs/. Configs/Quorra.entitlements and Configs/QuorraCLI.entitlements sit side-by-side. Both binaries are sandboxed and share an identical entitlement set; com.apple.security.inherit is explicitly absent because the CLI is never spawned as a child of the app.
  6. The ../Pacakges/INI typo is gone. Resolved as part of the fresh-start migration. The workspace now references Packages/QuorraCore directly and the pbxproj is clean of stale paths.
