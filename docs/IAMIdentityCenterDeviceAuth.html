01Overview

"IAM Identity Center sign-in" is shorthand for: drive the OAuth 2.0 device authorization grant (RFC 8628) against an AWS Identity Center start URL, hold the resulting bearer token, then use it to enumerate accounts/roles and exchange the (account, role) pair for short-lived STS-style credentials. Quorra is the orchestrator. The user-facing affordance is "Sign in to https://example.awsapps.com/start"; everything below that is plumbing.

There are three AWS service surfaces involved, all unauthenticated-or-token-authenticated (no SigV4):

  • SSO OIDC (oidc.<region>.amazonaws.com) — registers a public OAuth client and runs the device-code dance.
  • SSO Portal (portal.sso.<region>.amazonaws.com) — once you have an access token, lists assigned accounts/roles and mints role credentials.
  • STS only enters if you decide to AssumeRole further. For a default Identity Center sign-in you don't touch STS directly; GetRoleCredentials hands you the credential triple already.
scopeThis document is research, not a build plan. The SDK-for-Swift answers (especially "does the default token resolver write to ~/.aws/sso/cache?") are the load-bearing decisions. Everything else is well-trodden OAuth.

Why we don't shell out to aws sso login

That binary writes JSON files into ~/.aws/sso/cache/ as the source of truth, and the broader AWS tooling expects them there. Quorra wants secrets in the macOS Keychain, not a sandboxed app's view of ~/.aws/sso/cache. Owning the OIDC flow is the whole point — see CLAUDE.md § SSO Flow.

Two ways to ship this

Either talk the OIDC + Portal HTTP APIs directly with URLSession, or use the AWS SDK for Swift's SSOOIDC + SSO service clients. The SDK saves us request-shape bikeshedding and gives us first-party model evolution; the cost is an opinionated default token cache that we have to disable. Both options are detailed below.

02Device authorization grant (RFC 8628)

RFC 8628 defines a flow for clients on devices without a browser, or where the user shouldn't paste credentials into the device. Despite the name, it's the right shape for any native desktop app that wants to defer authentication to the system browser. AWS Identity Center implements it via the SSO OIDC service.

State machine

  1. Register. Client calls POST /client/register on the SSO OIDC endpoint with clientName, clientType: "public", and (for refresh-token issuance) the scope list ["sso:account:access"]. Response yields clientId, clientSecret, and clientSecretExpiresAt (Unix seconds, typically ~90 days).
  2. Start device authorization. Client calls POST /device_authorization with clientId, clientSecret, startUrl. Response: deviceCode, userCode, verificationUri, verificationUriComplete, expiresIn (lifetime of the device code, usually 600s), interval (minimum poll interval in seconds, usually 5s).
  3. User verification. Open verificationUriComplete in the system browser (it embeds the user code as a query param so the user doesn't have to type it). Display userCode as a fallback if the URL fails to launch.
  4. Poll for token. Client polls POST /token with grantType: "urn:ietf:params:oauth:grant-type:device_code", clientId, clientSecret, deviceCode. Wait at least interval seconds between polls; if the server responds slow_down, increase the interval by 5s.
  5. Success. POST /token returns accessToken, tokenType: "Bearer", expiresIn, optionally refreshToken, optionally idToken. Persist all of it.
  6. Refresh. Later, when the access token nears expiry, call POST /token with grantType: "refresh_token" and the stored refresh token. AWS only returns refresh tokens when the registered scope set includes sso:account:access.

Polling rules — the parts that bite

RFC 8628 §3.5 is short but the details matter:

  • The first poll should not happen earlier than interval seconds after the device authorization response — clients that fire immediately routinely get slow_down.
  • On authorization_pending, keep the same interval and try again.
  • On slow_down, add 5 seconds to the current interval and try again. The increase is permanent for the rest of the flow, not just the next poll.
  • On expired_token or access_denied, stop polling immediately. The user must re-initiate.
  • Stop polling when the wall clock since step 2 exceeds expiresIn seconds — even if the server hasn't said so. Treat that as expired_token.

Error codes

  • authorization_pendingUser hasn't completed the browser step yet. Continue polling at the current interval.
  • slow_downYou're polling too fast. Add 5s to the interval and continue.
  • access_deniedUser refused or the browser flow was cancelled. Surface as a clean cancellation, not an error.
  • expired_tokendeviceCode is past its expiresIn. The user has to start over.
  • invalid_grantThe grant or device code is malformed. Programming bug — not a user-recoverable state.
  • invalid_clientThe clientId/clientSecret are wrong or expired. Re-run RegisterClient and retry.

Reference: RFC 8628 — OAuth 2.0 Device Authorization Grant, especially §3.4 (token request) and §3.5 (device access token response).

03AWS SSO OIDC API

Reference: AWS IAM Identity Center OIDC API Reference. Three operations are load-bearing for sign-in.

operationRegisterClient

Registers a public OAuth 2.0 client. Returns a clientId/clientSecret pair Quorra reuses across many sign-ins until clientSecretExpiresAt elapses. Cache it in the Keychain — re-registering on every launch is wasteful and the dashboard shows the user a "registered apps" entry per registration.

POST https://oidc.<region>.amazonaws.com/client/register { "clientName": "Quorra", "clientType": "public", "scopes": ["sso:account:access"] } → { "clientId", "clientSecret", "clientIdIssuedAt", "clientSecretExpiresAt" }

Including scopes: ["sso:account:access"] is what unlocks refresh-token issuance later. Without it, CreateToken will not return a refreshToken and you're stuck redoing the device dance every ~8 hours.

operationStartDeviceAuthorization

Begins the device-grant flow. Echoes the start URL chosen by the user back into the verification URI so the auth portal knows which Identity Center instance to authenticate against.

POST https://oidc.<region>.amazonaws.com/device_authorization { "clientId", "clientSecret", "startUrl": "https://example.awsapps.com/start" } → { "deviceCode", "userCode", "verificationUri", "verificationUriComplete", "expiresIn", "interval" }

operationCreateToken (initial)

Polled until the user completes the browser step. Returns the SSO access token used against the Portal API.

POST https://oidc.<region>.amazonaws.com/token { "clientId", "clientSecret", "deviceCode", "grantType": "urn:ietf:params:oauth:grant-type:device_code" } → { "accessToken", "tokenType": "Bearer", "expiresIn", "refreshToken"?, "idToken"? }

operationCreateToken (refresh)

Same endpoint, different grant. Use when the access token is expiring and a refresh token is on hand. Returns a fresh access token and (usually) a rotated refresh token; replace both atomically in the Keychain.

POST https://oidc.<region>.amazonaws.com/token { "clientId", "clientSecret", "grantType": "refresh_token", "refreshToken": "<previous refresh token>" } → { "accessToken", "expiresIn", "refreshToken" }

If the refresh token is itself revoked or expired, this returns InvalidGrantException. Treat that as "fall back to the full device flow" — silently if the user is already in front of the app, or with a notification banner if Quorra is acting in the background.

Endpoint regionality

Pick the region from the region in the user's [sso-session] block. Identity Center instances are regional; talking to the wrong region returns InvalidRequestException. The StartUrl alone does not encode the region.

04AWS SSO Portal API

Reference: AWS IAM Identity Center Portal API Reference. All three operations take the SSO access token as a header (x-amz-sso_bearer_token in the SDK; the SDK does this automatically).

operationListAccounts

Pages the AWS accounts the user is assigned to. Quorra calls this once after sign-in to populate the account picker; cache the result alongside the token until expiry.

GET https://portal.sso.<region>.amazonaws.com/assignment/accounts Headers: x-amz-sso_bearer_token: <accessToken> → { "accountList": [{ accountId, accountName, emailAddress }], "nextToken"? }

operationListAccountRoles

Pages the IAM Identity Center permission sets the user can assume in a given account.

GET https://portal.sso.<region>.amazonaws.com/assignment/roles?account_id=<id> Headers: x-amz-sso_bearer_token: <accessToken> → { "roleList": [{ accountId, roleName }], "nextToken"? }

operationGetRoleCredentials

Mints short-lived credentials for an (account, role) pair. This is the call that produces the AccessKeyId/SecretAccessKey/SessionToken/Expiration tuple Quorra serves to consumers (CLI, IMDS).

GET https://portal.sso.<region>.amazonaws.com/federation/credentials?account_id=<id>&role_name=<name> Headers: x-amz-sso_bearer_token: <accessToken> → { "roleCredentials": { accessKeyId, secretAccessKey, sessionToken, expiration } }

expiration is Unix milliseconds. Lifetime is configurable on the permission set (1h default, max 12h). Quorra should always treat it as "could be as low as 1 hour" and refresh proactively.

quotasThe Portal API is rate-limited per access token; GetRoleCredentials in particular is documented to throttle aggressively. Cache the credential triple and refresh at expiration - 5min, not on every CLI invocation.

05AWS SDK for Swift

Source of truth: awslabs/aws-sdk-swift. The SDK is a SwiftPM package; pulling in AWSSSOOIDC and AWSSSO as products is enough.

The two clients we care about

TypeModulePurpose
SSOOIDCClientAWSSSOOIDCWraps RegisterClient / StartDeviceAuthorization / CreateToken. The shape we drive the device flow through.
SSOClientAWSSSOWraps ListAccounts / ListAccountRoles / GetRoleCredentials. The Portal calls.

Both expose async/await methods that mirror their REST shapes 1-to-1 — registerClient(input:), startDeviceAuthorization(input:), createToken(input:), listAccounts(input:), listAccountRoles(input:), getRoleCredentials(input:). Region is passed via the client config; talking to oidc.eu-west-1.amazonaws.com means SSOOIDCClient.Config(region: "eu-west-1").

let oidc = try SSOOIDCClient(region: "eu-west-1")

let reg = try await oidc.registerClient(input: .init(
    clientName: "Quorra",
    clientType: "public",
    scopes: ["sso:account:access"]
))
// reg.clientId / reg.clientSecret / reg.clientSecretExpiresAt

The auth-side extension points

Outside of SSOOIDCClient (which is unauthenticated for RegisterClient and StartDeviceAuthorization, then takes the OIDC client credentials inline for CreateToken), every other AWS SDK call needs an identity. The SDK abstracts this through SmithyIdentity.IdentityResolver:

ProtocolModuleRole
IdentityResolverSmithyIdentityGeneric root protocol — returns an Identity on demand.
AWSCredentialIdentityResolverSmithyIdentitySpecialised to AWSCredentialIdentity (the SigV4 triple). What you'd plug into a downstream S3Client if you wanted to use Quorra creds with the SDK.
SSOTokenIdentityResolverAWSSDKIdentitySpecialised to the SSO bearer token. Has a default that reads the JSON cache files in ~/.aws/sso/cache/; this is the one we want to override.

Both SSOClient and SSOOIDCClient accept the resolver via their config: the property is typed as any AWSCredentialIdentityResolver (for SSOClient when used through the credential-provider chain) or as a token resolver attached to specific operation inputs. Plug in your own type and the on-disk cache never gets consulted.

06Bypassing the on-disk cache

load-bearing answerYes — the AWS SDK for Swift's default SSO token resolver reads and writes ~/.aws/sso/cache/<sha1(startUrl)>.json. This matches the AWS CLI / boto3 behaviour and is the file we explicitly do not want Quorra to touch.

Where the on-disk behaviour comes from

It's not in the OIDC client itself — SSOOIDCClient's createToken just performs an HTTP request and returns CreateTokenOutput. The disk dance is in the credential provider chain: when an SDK client (e.g. S3Client) is constructed with no explicit credentials, the chain looks for a [sso-session] in ~/.aws/config, then expects to find a matching cached token JSON under ~/.aws/sso/cache/. If the token is missing or expired, the chain (depending on the SDK version) attempts a refresh via CreateToken and writes the refreshed value back to disk. The exchange to the role triple via GetRoleCredentials is similarly cached at ~/.aws/cli/cache/ by some implementations.

How to skip it cleanly

Two compatible strategies:

  1. Don't use the chain. Build SSOOIDCClient and SSOClient directly, pass the SSO access token explicitly as the accessToken field on each operation input (ListAccountsInput.accessToken, GetRoleCredentialsInput.accessToken, etc.). Quorra controls the bytes; nothing reads ~/.aws/sso/cache/ because the resolver is never asked.
  2. Conform to SSOTokenIdentityResolver. If, later, we wire other SDK clients (S3Client, EC2Client) so they can resolve credentials through the chain transparently, supply our own token resolver that reads from the Keychain instead of the cache file. Set it on the client config; the chain calls it instead of the file-backed default.

For Quorra v1, strategy (1) is correct: we never construct downstream service clients in the app — we expose role credentials to outside processes via the IMDS server and stdout (credential_process). Strategy (2) is the mode if we ever embed an AWS SDK client.

Sketch of a Keychain-backed token resolver

KeychainSSOTokenResolver.swift swift 
import SmithyIdentity
import AWSSDKIdentity

// Conform to SSOTokenIdentityResolver — same shape the default
// FileBasedSSOTokenIdentityResolver uses, but reads the Keychain.
struct KeychainSSOTokenResolver: SSOTokenIdentityResolver {
    let sessionName: String      // e.g. "corp-sso"
    let keychain: Keychain          // Quorra's wrapper

    func getIdentity(
        identityProperties: Attributes?
    ) async throws -> SSOTokenIdentity {
        let stored = try keychain.readToken(forSession: sessionName)

        if stored.isExpired(skew: 60) {
            let refreshed = try await DeviceAuth.refresh(stored)
            try keychain.writeToken(refreshed, forSession: sessionName)
            return SSOTokenIdentity(
                token: refreshed.accessToken,
                expiration: refreshed.expiresAt
            )
        }
        return SSOTokenIdentity(
            token: stored.accessToken,
            expiration: stored.expiresAt
        )
    }
}

Wire it onto a client by mutating the client config:

attach-resolver.swift swift 
var cfg = try await SSOClient.Config(region: region)
cfg.tokenIdentityResolver = KeychainSSOTokenResolver(
    sessionName: "corp-sso",
    keychain: keychain
)
let sso = SSOClient(config: cfg)
verify the property nameThe exact field on the generated Config has shifted between SDK versions (tokenIdentityResolver / bearerTokenIdentityResolver). Check against the version pinned in Package.resolved at integration time. The protocol surface is stable; the config plumbing has churned.

07Apple frameworks for the verification step

The user-verification step opens verificationUriComplete in a browser. Two viable choices on macOS:

APIModuleBehaviour
ASWebAuthenticationSessionAuthenticationServicesIn-app web view that shares cookies with Safari, hands back a result on a chosen redirect URI scheme.
NSWorkspace.shared.open(_:)AppKitHands the URL to the user's default browser. App keeps polling CreateToken; nothing comes back through Apple — completion is observed on the wire.

Recommendation: NSWorkspace.shared.open

Three reasons:

  • No redirect URI. RFC 8628 explicitly removes the redirect-URI step — the user authenticates entirely on the IdP's portal, and the device app learns about completion via polling. ASWebAuthenticationSession's API is built around a callback URL; using it for a flow that has no callback URL is fighting the framework.
  • Default browser, default cookies. The corporate Identity Center portal almost certainly already has the user signed in to the corp IdP in their everyday browser. Routing them through that browser turns "click this once" into "click confirm." ASWebAuthenticationSession's ephemeral cookie jar (prefersEphemeralWebBrowserSession = true) loses that benefit; non-ephemeral mode is allowed but presents a system "quorra wants to use awsapps.com to sign in" prompt that's confusing for an internal corporate flow.
  • Sandbox-friendly. NSWorkspace.open is permitted from a sandboxed app without entitlements. ASWebAuthenticationSession works too, but the path of least resistance is the simpler one.
open-verification.swift swift 
import AppKit

guard let url = URL(string: deviceAuth.verificationUriComplete) else {
    throw DeviceAuthError.malformedVerificationURL
}
// Returns false if no app could handle the URL — fall back to
// surfacing the userCode in a copyable label.
let opened = NSWorkspace.shared.open(url)

Surface the userCode in the UI alongside the auto-launch — copy-on-click, with a visible "if your browser didn't open, paste this code at verificationUri" affordance. Some browsers eat verificationUriComplete's query parameters when launched cold; the manual fallback covers it.

When ASWebAuthenticationSession would be right

If we ever switch to the standard authorization-code grant (which does have a redirect URI), ASWebAuthenticationSession is the correct primitive. That's not where Quorra v1 is going.

08Keychain layout

All Quorra SSO state goes into kSecClassGenericPassword items in the shared access group declared in both target entitlements: $(AppIdentifierPrefix)dev.ajbeck.quorra.shared. The CLI and the app read/write the same items.

Item conventions

Itemserviceaccountsecret
OIDC client registrationdev.ajbeck.quorra.oidc-client<region>JSON: { clientId, clientSecret, expiresAt }
SSO access & refresh tokendev.ajbeck.quorra.sso-token<sso-session-name>JSON: { accessToken, expiresAt, refreshToken? }
Role credentialsdev.ajbeck.quorra.role-creds<accountId>:<roleName>JSON: { accessKeyId, secretAccessKey, sessionToken, expiration }

One row per (service, account) pair. Updates use SecItemUpdate; missing-row updates fall back to SecItemAdd. Deletes use SecItemDelete. Round-tripping is straightforward as long as the access group attribute is set on every operation.

Accessibility class

Two reasonable choices:

ConstantVisibilityUse case
kSecAttrAccessibleWhenUnlockedMac unlocked, current login sessionHighest secrecy. Items unreadable when the screen is locked. Right for the SSO refresh token.
kSecAttrAccessibleAfterFirstUnlockAfter first unlock since bootTolerates background access while the screen is locked. Right for short-lived role creds the IMDS server might serve to a build script while the user is away from their desk.

Recommended split: refresh token uses WhenUnlocked, access token + role credentials use AfterFirstUnlock. The refresh token is the long-lived secret; treat it strictly. Access tokens are ~8h and role creds are ~1h — a screen lock shouldn't break a backgrounded build that needs them. WhenUnlockedThisDeviceOnly / AfterFirstUnlockThisDeviceOnly variants prevent items from being copied to a new Mac via Migration Assistant; opt for the ThisDeviceOnly variant — credentials shouldn't ride along on hardware migration.

Concurrent safety

Both binaries can mutate Keychain items simultaneously. Keychain operations are themselves atomic per call, but a read-modify-write sequence (refresh-then-store) is not. Wrap the refresh path in an actor or use a process-shared lock file (flock on a file under the shared container). Per CLAUDE.md § App ↔ CLI Architecture we already plan for shared mutable state; the same locking discipline applies here.

do not write secrets to ~/.aws/credentialsThe whole point of the Keychain layer is that ~/.aws/credentials stays free of bearer tokens, refresh tokens, and SigV4 secrets. The on-disk file holds metadata and pointers; secrets live exclusively in Keychain items reachable through the shared access group.

09Lifetimes & "active" semantics

"Active" — what the green dot means

For the sidebar status indicator on a profile, "active" should mean: Quorra can serve fresh role credentials for this profile right now without user interaction. That's a four-clause check:

  1. The sso-session referenced by the profile has an SSO access token in the Keychain whose expiresAt is in the future, or a refresh token is present and the access token can be silently refreshed.
  2. The OIDC client registration is not past clientSecretExpiresAt (or the refresh path will tear down with InvalidClientException).
  3. The most recent GetRoleCredentials call for this (account, role) succeeded — i.e. the user still has the role assigned.
  4. If role credentials are cached, their expiration is in the future or we still have a valid access token to mint new ones.

If (1) and (2) hold but the cached role creds are stale, we count as "active" — the next consumer call will trigger a transparent GetRoleCredentials. If (1) is false and no refresh token is on hand, we are not active regardless of what's cached; the dot is amber/red and clicking the profile prompts a new device-flow sign-in.

Refresh windows

Don't wait until expiry. Refresh proactively on a 60-second skew:

  • Access token: refresh when expiresAt - now < 5min.
  • Role credentials: re-fetch when expiration - now < 5min.
  • OIDC client: re-register when clientSecretExpiresAt - now < 7 days (any refresh attempt will surface InvalidClientException if we leave it).

10End-to-end Swift sketch

Pulling the pieces together: the high-level shape of the sign-in path, plus how the Keychain-backed token feeds the Portal calls.

DeviceAuth.swift swift 
import AppKit
import AWSSSOOIDC
import AWSSSO

struct DeviceAuth {

    let session: SSOSession     // startUrl, region, scopes
    let keychain: Keychain

    func signIn() async throws -> StoredToken {
        let oidc = try SSOOIDCClient(region: session.region)

        let reg = try await ensureClientRegistration(oidc)
        let dev = try await oidc.startDeviceAuthorization(input: .init(
            clientId: reg.clientId,
            clientSecret: reg.clientSecret,
            startUrl: session.startUrl
        ))

        _ = NSWorkspace.shared.open(URL(string: dev.verificationUriComplete!)!)

        var interval = TimeInterval(dev.interval ?? 5)
        let deadline = Date().addingTimeInterval(TimeInterval(dev.expiresIn ?? 600))

        while Date() < deadline {
            try await Task.sleep(for: .seconds(interval))
            do {
                let tok = try await oidc.createToken(input: .init(
                    clientId: reg.clientId,
                    clientSecret: reg.clientSecret,
                    deviceCode: dev.deviceCode,
                    grantType: "urn:ietf:params:oauth:grant-type:device_code"
                ))
                let stored = StoredToken(from: tok)
                try keychain.writeToken(stored, forSession: session.name)
                return stored
            } catch let e as AuthorizationPendingException {
                _ = e // keep polling at current interval
            } catch is SlowDownException {
                interval += 5
            } catch is ExpiredTokenException {
                throw DeviceAuthError.expired
            } catch is AccessDeniedException {
                throw DeviceAuthError.cancelled
            }
        }
        throw DeviceAuthError.expired
    }

    func roleCredentials(account: String, role: String)
        async throws -> RoleCredentials {

        let token = try await ensureFreshToken()
        let sso = try SSOClient(region: session.region)
        let resp = try await sso.getRoleCredentials(input: .init(
            accessToken: token.accessToken,
            accountId: account,
            roleName: role
        ))
        guard let creds = resp.roleCredentials else {
            throw DeviceAuthError.malformedResponse
        }
        return RoleCredentials(from: creds)
    }
}

The ensureFreshToken path is the Keychain-backed resolver from §06: read the stored token, refresh via CreateToken(refresh_token) if it's near expiry, return the live access token. SSOClient takes the bearer token directly on each input — nothing in this code path consults ~/.aws/sso/cache/.

11Errors & their handling

  • .authorizationPendingMaps from AuthorizationPendingException. Internal, never surfaces — the polling loop swallows it.
  • .slowDownMaps from SlowDownException. Internal — the loop increments the interval by 5s.
  • .expiredUser did not complete the browser step before expiresIn. Surface a "sign-in expired, try again" toast and offer to restart.
  • .cancelledUser refused at the IdP. Treat as a clean cancellation — no error toast, return to the previous UI state.
  • .invalidClientClient registration is gone or expired. Re-register and retry once; if the second attempt fails, surface as a real error.
  • .invalidGrantRefresh token is no longer valid. Drop it from the Keychain and re-run the device flow.
  • .networkUnavailableURLSession-level failure. Retry with backoff; offer the user a manual retry button after two failures.
  • .throttlingPortal API rate limit. Back off and retry; if it persists, the user is hitting an org-level cap and we should surface that.

12Open questions

●SDK version pinning ●Resolver field name ●OIDC client per region ●Per-binary OIDC client ●Refresh-token lifetime ●Multi-session UX

Should the OIDC client be per-region?

The OIDC service is regional, but a registered client can be reused across regions for the same Identity Center start URL. We tentatively scope items by region in the Keychain because the registration endpoint changes; cross-checking against a multi-region tenant is required before shipping.

Should the app and the CLI share one OIDC client registration?

Yes — they're the same product, the same access group, and AWS bills "registered apps" cosmetically. Both binaries should look up (service: dev.ajbeck.quorra.oidc-client, account: <region>) and only register if missing. The first to wake up wins and the other reads the result.

What is the actual refresh-token lifetime?

Not documented numerically by AWS. Empirical reports suggest weeks but it's at the IdP's discretion. Quorra should treat any InvalidGrantException on refresh as "fall back to the full device flow" and not assume a TTL.

How do we present multiple [sso-session] blocks?

One sign-in per session. The sidebar groups profiles under their session header (already designed in SidebarGroups); the green-dot status is per-session, then propagates down to the profiles that reference it. Edge case: a profile with sso_start_url set inline (no session block) gets its own implicit session.

Do we need the idToken?

No. CreateToken sometimes returns an idToken; we ignore it. AWS doesn't require it for GetRoleCredentials, and we have no use for the JWT claims. Storing it would just be one more rotated secret to manage.

SDK version pinning

The exact Config field for token resolver injection has changed between recent aws-sdk-swift releases. Pin the SDK to a specific minor version in Package.resolved and verify against the generated headers at integration time. Don't follow main.
